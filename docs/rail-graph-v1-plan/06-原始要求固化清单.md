# 原始要求固化清单（对照基线）

> 目的：将用户最初输入的浓缩要求固定为“不可丢失的核对项”，用于后续逐项比对设计是否实现、偏离或需调整。
> 　注意，　这里是自然语言和隐含条件的简单叙述，　并非精确要求，　但是应当尽可能对齐，　或者根据实际修改．

## A. 项目阶段与边界

1. 当前阶段以“设计 schema + 指定交互/算法/逻辑/流程”为主。
2. 在设计完成与接口定型前，不接入现有应用运行链。
3. 设计可参照现应用，但不拘泥于当前单一类型结构。
4. 需要在新文件夹中推进，严格 TypeScript。
5. 需提供测试用例规划与早期增改调试接口。

## B. 时间模型要求（必须覆盖）

1. 支持基于运行顺序的简化时间模型（数值顺序，来自新 utils）。
2. 支持结合时刻表以及顺序插值和速度/停站时间常识推断的时间戳顺序。
3. 对中间时刻支持自动生成（插值/推断）。
4. 事件必须具备顺序标识；可选时间戳标识。

## C. 地理与图结构要求（必须覆盖）

1. 容纳并存储所有要素与标签：
   - 站台(poly, 需要与站线语义绑定)
   - 站线/股道(线路multilinestring的部分, 但是为了实现标识, 可能需要提取和渲染时拼接)
   - 道岔(point)
   - 复线结构(必须, 考虑动态垂直偏移/物理数据两种可能的实现)
   - 存车线(可选, 运行时通常不直接经由, 但是有特殊意义)
   - 桥隧上下行分离(现已有, 但是需要更加明确命名和语义)
2. 形成可运行的图论结构，而非仅线性线段拼接。
3. 支持两类路径决策：
   - 可显式指定经由/上下行区间
   - 可按标签或规则自动解析与挑选
4. 能确定点与线在运行时的唯一顺序（可指定或自动决定）。

## D. 事件层要求（必须覆盖）

1. 支持以下事件类型的生成能力：
   - 停靠站台
   - 跨越站台（不停）
   - 经过道岔
   - 经过特殊区间
   - 行先车种更换/运行系统变更（沿用上版思路）
   - 其他固定的特殊事件, 例如编组解挂作业
   - "车窗绝景", 一种模式包含地理方向, 角度范围, 距离, 另一种模式为固定地图点. 需要支持介绍文字, 图片链接.
   - 应用中用户创建的其他事件(后续支持, 基础必须有)
2. 事件应具备顺序与时间戳标识生成能力。
3. 当前阶段只要求结构与正确性，硬性要求编辑输出接口能力, 不要求完成最终渲染。

## E. 兼容与容错要求（必须覆盖）

1. ORM 数据不一致和缺失是常态，系统必须可随时增改。
2. 必须具备自动补充缺失数据能力。
3. 容错目标是“不至于出错，符合常理”，而非过度中断。
4. 补全与修正应可追踪，便于后续人工审阅。

## F. 与历史能力的关系（必须继承）

1. 保留并兼容既有最基础能力：
   - 基于 geojson 自定义字段的上下行分离
   - 环线几何处理
2. 保留并吸收上一开发版兼容层方向：
   - 途中事件
   - 列车跨线
   - 车中变更运行系统
3. 新系统应整合上述能力，而非割裂重做。

## G. 输出交付要求（本轮文档层面）

1. 文档中需精确到 TS 每个文件：
   - 做什么
   - 提供哪些结构
   - 提供哪些接口与方法
2. 文档需明确“最终跑起来流动的是哪些核心数据”。
3. 文档用于后续逐文件详细确认与逐项比对。
