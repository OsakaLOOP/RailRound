# Rail Graph v1 原始设计偏离审计与产品接入修正

阶段级执行总结见 [`13-阶段变更验收与最终成品总结.md`](./13-阶段变更验收与最终成品总结.md)。

## 1. 审计结论

本轮审计对照了以下原始设计入口：

- `docs/rail-graph-v1/14-决策中间件与对外接口草稿.md`
- `docs/rail-graph-v1/16-参数传递与内容寻址对比.md`
- `docs/rail-graph-v1/17-编译框架-冷热分层-增量与反向索引.md`
- `docs/rail-graph-v1/user-event-mileage-layer.md`
- `docs/rail-graph-v1-plan/04-核心数据流与运行核心数据.md`
- `docs/rail-graph-v1-plan/07-GeoJSON与JSON层级契约.md`

总体判断：

1. PR0-PR8 没有偏离 `SystemContext -> RunContext -> TripResult` 的主链，反而把 MVP/aggregate 的验证资产接入了正式 runtime。
2. 主要偏离出现在用户端契约：先前实现把 `RunPath`、`ResolvedGeoJsonPath`、`patternRef` 等内部运行结构暴露到了 `TripResult` / `TripPlanRequest` 上，容易把产品接口退化为半成品 MVP 调试接口。
3. mileage UserEvent 的方向是正确的：以里程为主锚，不让站/时间/坐标成为存储真源。但适配层仍过度依赖 `TripResultSegment.resolvedPath`，说明用户数据消费与内部 runtime artifact 边界不够清楚。

本轮修正不回滚已超额完成的 runtime/deployment/mileage 接入，而是在其上分离产品结果和内部 bridge 数据。

## 2. 原始设计继承情况

| 原始目标 | 当前状态 | 证据 |
|---|---|---|
| 编译期与运行期分离 | 已继承 | `SystemContext`、`RunContext`、`run-resolver.ts`、集成 gate |
| 内容寻址与可复现运行 | 已继承 | `graphId`、`fingerprints`、`runId`、`presetHashes` |
| 管理员 ServicePattern 与用户运行输出分离 | 基本继承 | `buildDeployedSystem()`、`PathPreset`、`planTrip()` |
| 用户端优先消费 preset 或站点请求 | 本轮修正 | `TripPlanRequest` 不再要求 `patternRef` |
| 跨 ServicePattern transfer 自动发现 | 本轮补齐最小产品链路 | `planTrip()` 根据 stationSequence 交集生成多段 TripResult |
| 用户端结果可直接渲染和保存 | 本轮加强 | `TripResultSegment.geometry/events/mileageProfile` |
| 用户事件不参与寻路 | 已继承 | `mileage-events.ts`、`mileageUserEvents.ts`、runtime adapter 测试 |
| legacy app 数据兼容 | 已继承 | `railGraphTripAdapter.ts`、`mileageUserEvents.ts`、旧 routing 回归 |

## 3. 发现的偏离与修正

| 偏离 | 风险 | 修正 |
|---|---|---|
| `TripPlanRequest` 暴露 `patternRef` | 普通用户请求被迫理解 ServicePattern，偏向 admin/MVP 内部结构 | 移除请求层 `patternRef`，由 planner 在 `SystemContext` 内按站点覆盖自动选择候选 pattern |
| `TripResult.internalRunPaths` | 用户保存结果直接携带内部运行路径，和“用户不可见”设计冲突 | 移除公开字段，改由 `PlanTripResult.runtimeArtifacts` 单独返回 |
| `TripResultSegment.resolvedPath` | 用户结果包含内部 geometry/station passage 全结构，后续 schema 难稳定 | 新增 `TripSegmentMileageProfile`，只暴露用户事件投影和保存需要的里程 profile |
| `TripResultSegment.patternRef/lineRef/systemRef/direction` 混在产品字段里 | UI 展示字段、用户数据锚点、内部模板引用边界不清 | 公开段只保留展示/几何/事件/里程 profile；legacy app bridge 从 `runtimeArtifacts` 或 `mileageProfile` 读取兼容字段 |
| `eventTypeSummary` 使用 `RunEventType` | 用户端看到内部事件枚举，如 `scenic_view` | 改为用户事件类型 `stop/pass/transfer/scenic/note` |
| mileage runtime adapter 从 `resolvedPath` 重建 context | 用户事件消费依赖内部 path artifact | 改为从 `TripSegmentMileageProfile` 构建 projection context |
| 自由规划无法跨 ServicePattern | 原始设计要求自动从 stationSequence 交集推导 transfer；单 pattern 限制会让产品规划像半成品 demo | 在 runtime planner 内实现轻量 transfer graph；当无单 pattern 覆盖时，按共享站搜索多 hop，并输出多 segment TripResult 与 transfer 事件 |
| `RunSpec.start/end` 未裁切 ServicePattern | 用户选择 B→C 仍可能得到 A→C 全路径，影响多段 transfer 的真实可用性 | `resolveRunPath()` 根据起终点裁切 trace/edge/pathSegments，并规范 orderIndex |

## 4. 修正后的产品契约

### 4.1 用户端规划请求

```ts
interface TripPlanRequest {
  presetId?: string;
  systemId: string;
  startStationRef: EntityRef;
  endStationRef: EntityRef;
  viaRefs?: EntityRef[];
  directionPreference?: string;
  date?: string;
}
```

普通用户请求只有 preset 或站点/方向约束，不需要知道 `ServicePattern.patternId`。

### 4.2 用户端规划结果

`TripResult` 只保留可展示、可保存、可被用户事件消费的数据：

- `segments[].geometry`
- `segments[].events`
- `segments[].viaStations`
- `segments[].mileageProfile`
- `totalDistanceKm` / `totalTimeMinutes`
- `routeFingerprint`

其中 `mileageProfile` 是产品级投影数据，允许用户事件、搜索、保存行程复用；它不是完整 `RunPath` 或 `ResolvedGeoJsonPath`。

### 4.3 内部 bridge artifact

`PlanTripResult` 成功时返回：

```ts
{
  status: "ok";
  trip: TripResult;
  runtimeArtifacts: TripRuntimeArtifacts;
}
```

`runtimeArtifacts` 用于当前 app adapter、debug、迁移期 legacy bridge。它可以包含 `RunPath` 与 `ResolvedGeoJsonPath`，但不是用户端展示和保存的默认 schema。`SavedTrip.runtimeArtifacts` 为可选字段，只用于需要复现内部运行时的保存场景。

## 5. 与原始文档的允许差异

| 差异 | 是否允许 | 原因 |
|---|---|---|
| `TripResult.planUsed` 从 `confirmed_template` 改为 `auto` | 允许 | 用户侧语义应是 preset / auto，而非内部模板确认状态 |
| `TripResult` 不再内联 `internalRunPaths` | 必须修正 | 原文虽有字段示例，但同时明确“用户不可见”；公开类型内联会造成误用 |
| `TripSegmentMileageProfile` 新增 | 允许且必要 | mileage UserEvent 已成为产品面，需要稳定、比 `ResolvedGeoJsonPath` 更窄的数据消费契约 |
| `PlanTripResult.runtimeArtifacts` 新增 | 允许 | 保留调试/adapter 能力，同时隔离产品 schema |
| 自由规划包含共享站 transfer 最小实现 | 允许但需继续加强 | 已消除 patternRef 外露，并支持 stationSequence 交集拆分多段；显式换乘关系、步行时间和时刻表等待评分仍属后续增强 |

## 6. 阶段验收

本轮修正的直接验收：

```powershell
npx vitest run src/__tests__/rail-graph-trip-planner.test.ts src/__tests__/mileage-events-runtime-adapter.test.ts
npx tsc --noEmit -p tsconfig.json
```

覆盖内容：

1. preset 规划仍可生成 `TripResult`。
2. 站点请求不传 `patternRef` 也能得到 `planUsed="auto"`。
3. `TripResult` 不包含 `internalRunPaths`。
4. `TripResultSegment` 不包含 `resolvedPath` / 顶层 `patternRef`。
5. `runtimeArtifacts` 单独携带内部 run/path bridge 数据。
6. mileage UserEvent 使用 `TripSegmentMileageProfile` 投影，不再依赖公开 `resolvedPath`。
7. 单段 `RunSpec.start/end` 会裁切 confirmed template，而不是默认整条 ServicePattern。
8. A→D 这类跨 ServicePattern 请求可通过共享站 C 自动拆成两段，并在第二段开头插入 `transfer` TripEvent。

完整回归仍以：

```powershell
npm run rail:integration:verify
```

为最终门禁。

## 7. 后续缺口

| 缺口 | 影响 | 下一步 |
|---|---|---|
| DeployedSystem 尚未成为 app 全局默认数据源 | app 仍以旧 `railwayData` 为主，rail-graph 是 adapter 旁路 | 增加部署包加载/选择入口，再逐步替换 planner 调用 |
| UI 未完整消费 rail-graph TripResult | 当前测试证明 adapter 可用，未证明全 UI 工作流切换 | 后续添加 map/records/stats/search smoke 或 Playwright 覆盖 |
| runtimeArtifacts 保存策略曾待定 | 有 debug 价值，但不适合成为所有用户保存记录的默认字段 | 已在 app `Trip.railGraph.tripResult` 保存产品快照，默认不保存 `runtimeArtifacts`；Edge API 与 app load round-trip 已验证保留产品快照 |
| transfer 搜索仍是最小实现 | 支持共享站自动 transfer，但尚未引入步行换乘、显式 transfer relation 权重、时刻表接续评分 | 后续把 aggregate transfer relation 和 timetable wait cost 纳入 scorer |

这些缺口不推翻 PR0-PR8 的成果；它们是从 MVP/aggregate 走向完整产品集成的下一组明确任务。
