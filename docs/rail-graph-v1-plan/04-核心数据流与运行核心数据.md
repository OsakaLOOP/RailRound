# 核心数据流与运行核心数据

## 1. 主数据链（最终跑起来流动的数据）

统一主链：
`SourceInput → NormalizedEntityBatch → SystemContext(graphId+graph) → RunSpec → RunContext(runId+spec) → resolveRunPath → buildRenderPlan → buildRunOrder → synthesizeTimeline → resolveAnchors → generateEvents → RunSnapshot → EditableSnapshot`

Graph 层（一次构建）与 Run 层（多次求解）分离。SystemContext 是共享根，RunContext 是每次求解的独立上下文。

## 2. 各阶段核心数据

### 2.1 SourceInput
- 来源：ORM、OpenRailwayMap、legacy networkMeta、geojson 补充标签。
- 特征：字段可能缺失/不一致。
- 最小字段：`source`, `entityKind`, `rawPayload`。
- GeoJSON 输入必须区分 `platform_area/track_geometry/switch_point/special_section/scenic_anchor/manual_event_anchor` 等 kind。
- GeoJSON geometry 只表达原始几何与外部标签；进入运行前必须标准化。

### 2.2 NormalizedEntityBatch
- 作用：把多源数据拉平到统一实体集。
- 核心内容：
  - `nodes[]`：站、道岔、线端点、拆分边界、关键点
  - `edges[]`：股道/区段/方向边
  - `areas[]`：站台面、站场范围等面对象
  - `sections[]`：桥、隧、上下行分离等特殊区间
  - `relations[]`：层间关联（站-站台、服务线-基础边）
  - `servicePatterns[]`：上下行、复线、运行系统、服务别语义
  - `eventAnchors[]`：车窗绝景、作业事件、用户事件等空间/语义锚点
  - `provenance[]`：来源追踪

### 2.3 SystemContext

- 作用：Graph 级不可变容器，一次构建、多次 Run 共享。
- 核心内容：
  - `graphId: string` — sha256(canonicalJson(graph))
  - `graph: RailGraph` — 图本身
  - `diagnostics: Diagnostic[]`
  - `createdAt: string`
- 规则：
  - Graph 被 patch 修改 → 新 graphId → 新 SystemContext。
  - 旧 graphId 的缓存 RunContext 全部失效。
  - 跨系统换乘：不同 SystemContext 间的 ServicePattern 通过 InfraNode 交集检测，与 graph 边界无关。

### 2.3.1 RailGraph
- 作用：统一多层图运行基底。
- 核心结构：
  - `infraLayer`: 物理连通
  - `serviceLayer`: 上下行/复线经由/系统语义
  - `eventLayer`: 固定事件、车窗绝景、用户事件锚点与策略
  - `runtimeLayer`: 运行计划装配位
- 关键索引：
  - `nodeById`, `edgeById`, `adjacency`, `serviceBindings`
  - `areaById`, `sectionById`, `eventAnchorById`
- 关键规则：
  - 站台面通过 relation 绑定站线，不直接替代站线。
  - 道岔等点对象吸附到线的结果写入 adjacency 或诊断。
  - 复线必须至少具备真实物理 edge 或动态偏移计划之一，二者可同时存在。

### 2.4 RunContext

- 作用：Run 级不可变容器，每个 RunSpec 产生一个。各阶段逐步填充。
- 核心内容：
  - `runId: string` — sha256(graphId + canonicalJson(spec))
  - `graphId: string` — 指向 SystemContext
  - `graph: RailGraph` — SystemContext 的共享引用
  - `spec: RunSpec`
  - `path: RunPath | null`
  - `renderPlan: RenderGeometryPlan | null`
  - `order: RunOrder | null`
  - `timeline: TimelinePoint[] | null`
  - `resolvedAnchors: ResolvedEventAnchor[] | null`
  - `events: RunEvent[] | null`
  - `diagnostics: Diagnostic[]`
- 规则：
  - 每个阶段返回新 RunContext（不可变更新）。graph 是共享引用，在所有 RunContext 中指向同一块内存。
  - runId 绑定 (graphId, spec)，天然保证 graph 与 path 的一致性。

### 2.5 RunPath
- 作用：图上确定唯一运行路径（可解释）。
- 关键字段：
  - `edgeSequence[]`
  - `nodeSequence[]`
  - `chosenDirection`
  - `candidateScores[]`
  - `resolvedBy: auto|manual`
- 规则：
  - 用户事件不参与路径候选评分。
  - 存车线默认不参与普通 run，除非显式 override 或作业策略引用。

### 2.5.1 RenderGeometryPlan
- 作用：描述运行路径如何渲染，不改变拓扑真源。
- 关键字段：
  - `geometrySource: physical_edges|dynamic_offset|mixed`
  - `stitchedEdgeRefs[]`
  - `offsetSegments[]`
  - `smoothing[]`
  - `diagnostics[]`
- 规则：
  - 真实物理 edge 优先作为拓扑依据。
  - 动态偏移用于缺少真实复线几何、显示修正或调试对照。
  - 动态偏移在并线、分线、道岔、桥隧出入口必须有平滑连接计划。

### 2.6 RunOrder
- 作用：离散顺序骨架，供 timeline/events 共用。
- 关键字段：
  - `orderPoints[]`（顺序号 + 实体引用）
  - `boundaries[]`（关键边界：道岔、系统切换点）

### 2.7 Timeline
- 作用：把顺序骨架转为时间点。
- 关键字段：
  - `timelinePoints[]`:
    - `orderIndex`
    - `timestamp?`
    - `isSynthesized`
    - `sourceAnchorRef?`

### 2.8 EventStream
- 作用：输出有序事件序列（暂不要求最终渲染）。
- 关键字段：
  - `events[]`:
    - `eventId`
    - `eventType`
    - `orderIndex`
    - `timestamp?`
    - `entityRefs`
    - `payload`
- 覆盖事件：
  - 停靠站台、跨越站台、经过道岔、经过特殊区间
  - 系统/车种/服务别变更、跨线、同车直通
  - 编组/解挂作业
  - 车窗绝景
  - 用户创建事件

### 2.8.1 EventAnchorResolution
- 作用：把事件锚点解析到运行顺序、时间与运行方向。
- 关键字段：
  - `anchorRef`
  - `orderIndex?`
  - `timestamp?`
  - `entityRefs[]`
  - `geometryRef?`
  - `vehicleView?`
- 规则：
  - 车窗绝景可以由地图绝对方向换算为车窗侧与相对方向。
  - 用户事件只在时空语义上与车辆运行相对绑定，不参与寻路。

### 2.8.2 EditableSnapshot / PatchSet
- 作用：提供早期增改调试接口与编辑输出。
- `EditableSnapshot` 核心内容：
  - `graph`
  - `runPlans[]`
  - `pendingPatches[]`
  - `diagnostics[]`
- `PatchSet` 覆盖：
  - 图实体新增/更新
  - 几何替换
  - relation link/unlink
  - event anchor 新增/更新
  - event policy 更新
- 规则：
  - 自动补全与人工编辑都输出 patch，不直接修改原始输入源。
  - patch 必须可 preview/apply/export。

### 2.9 Diagnostics
- 作用：贯穿全流程记录补全、冲突、降级与失败。
- 关键字段：
  - `level`, `code`, `stage`, `message`, `context`

## 3. 关键流转规则

### 3.1 顺序先于时间
- `RunOrder` 必须先生成。
- `Timeline` 只在 `RunOrder` 基础上补充时间语义。

### 3.2 事件绑定双锚
- 每条事件必须至少绑定 `orderIndex`。
- 有时间时再绑定 `timestamp`，无时间不阻断事件输出。
- 用户事件与车窗绝景允许先绑定空间锚点，再由 `EventAnchorResolution` 绑定到运行顺序。

### 3.3 路径与事件可追溯
- `RunEvent` 必须能追溯到：
  - 来源边/点
  - 生成规则或输入锚点

### 3.4 缺失补全与诊断并行
- 补全不是隐式行为，必须写入 `Diagnostics`。
- 核心阶段出现 `fatal` 时停止该 run 后续阶段。

### 3.5 拓扑与渲染分离
- `RunPath` 只表达运行拓扑与顺序。
- `RenderGeometryPlan` 表达真实几何拼接、动态偏移、平滑连接。
- 动态偏移不得反写为真实物理 edge。

### 3.6 编辑输出闭环
- `EditableSnapshot` 是调试与人工审阅入口。
- `PatchSet` 是增改输出入口。
- 自动补全、用户事件新增、车窗绝景锚点更新都必须能落为 patch。

## 4. 与现有结构映射
- `TripSegment(lineKey, fromId, toId, loopVia)` -> `RunSpec` 的最小输入子集。
- `networkMeta(common/byDirection/subSegments/events/systems)` -> `serviceLayer` 语义源之一。
- `geo.worker` 几何切片结果 -> `RunPath` 几何表现层附属数据，不作为路径唯一真源。
- 现有 GeoJSON 自定义字段 -> `geojson-contracts.ts` adapter 的兼容输入，不作为核心弱类型字段继续扩散。
- 现有途中事件/系统变更 -> `EventAnchor` + `RunEvent`，并进入 `EventAnchorResolution`。

## 5. 输出给后续实现的最小闭环
最小可运行闭环（不接 UI）：
1. 输入一个 SourceBatch
2. 构建 RailGraph
3. 输入 RunSpec
4. 输出 RunPath + RenderGeometryPlan + Timeline + EventStream + Diagnostics
5. 导出 EditableSnapshot JSON 供人工校验
6. 支持 PatchSet preview/apply/export
