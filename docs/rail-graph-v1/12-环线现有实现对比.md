# 环线现有实现对比

> 逐项对比现有环线实现与新设计的对应关系，标注直接迁移、需要适配、缺失和冗余。

## 1. 环线检测

| 维度 | 现有实现 | 新设计 | 判定 |
|---|---|---|---|
| 数据源标记 | GeoJSON `properties.isLoop=true/false` → `RailwayLineMeta.isLoop` (parser.ts:91) | `LineTopology.topologyType: "cyclic"` (07#4.3) | ⬆️ 升级：从 bool 变为枚举 `linear/cyclic/branching` |
| 回退检测 | 首尾坐标距离 < 0.5km → 视为环线 (geo.worker.js:144, helper.js:156, tripCalculator.js:129) | 图构建阶段 BFS 闭合检测，结果写入 `cycleCheck` | ✅ 保留思路，从启发式升级为图论判定 |
| 人工优先 | 无（直接覆盖） | 源数据已标注 topology 时直接采用不重算 | ✅ 新增 |
| 判定时机 | 解析时 (parser) + 渲染时 (worker 回退) | 图构建时一次性判定 (graph-builder.ts) | ✅ 集中到单一阶段 |

**结论**：检测逻辑从"bool + 距离启发式"升级为"显式拓扑类型 + 图论闭合检测 + cycleCheck 元数据"。迁移风险低。

## 2. 环线方向参照系

| 维度 | 现有实现 | 新设计 | 判定 |
|---|---|---|---|
| 方向值 | `'up'` / `'down'` | `'up'` / `'down'` / `'clockwise'` / `'counterclockwise'` | ⬆️ 扩展 |
| 参照系定义 | 隐式：站序索引递增方向 = up = 内回り (parser.ts:144 反转后) | 显式：clockwise = 站序索引递增方向 (07#5.1) | ✅ 保留并文档化 |
| 关键行为 | parser 将环线首站之后全反转，使 up=forward iteration | normalizer/adapter 处理输入数据时标准化站序，不再依赖隐式反转 | ⚠️ 迁移关键点 |
| 非环线收到 cw/ccw | 不适用 (现有无 cw/ccw) | 降级为 unknown + 诊断 (07#5.1) | ✅ 新防御 |

**parser.ts:140-146 的站序反转逻辑** 是整个现有环线方案的基石：

```ts
// 现有代码
if (entry.meta.isLoop && entry.stations.length > 2) {
    const [first, ...rest] = entry.stations;
    rest.reverse();
    entry.stations = [first, ...rest];
}
```

这样做的效果是：反转后 `stations[0]→stations[1]→...→stations[N-1]→stations[0]` 对应"内回り/up/clockwise"。所有环线方向计算（`computeLoopVia` 的模算术）都依赖这个 invariant。

**新设计迁移方案**：adapter 在处理 ORM/GeoJSON 环线数据时可以保留此反转逻辑，但必须在 `normalizers.ts` 输出中显式写入 `LineTopology.cycleCheck` 而非依赖隐式站序约定。核心模块只读 `LineTopology` 做方向决策。

## 3. 方向决策算法

| 维度 | 现有实现 | 新设计 | 判定 |
|---|---|---|---|
| 核心算法 | `computeLoopVia`: `distUp = (ti - fi + n) % n`, `distDown = (fi - ti + n) % n`, 取 `<=` (railwayRouting.ts:331) | 同模算术 + 多层回退链 (10#2.3) | ✅ 核心算法直接迁移 |
| 等长处理 | `<=` 导致等长时选 up | 明确：等长时 clockwise 优先，仍不确定 warn 人工 (10#2.3) | ✅ 更精确 |
| viaRefs 参与 | `loopVia` 在 TripSegment 上作为独立字段 | `viaRefs[]` 承载 loopVia 语义，与 directionHint 冲突时优先 (07#5.1) | ⬆️ 语义归并 |
| 决策追溯 | 无记录 | `RunPath.loopDecision` 记录 directionSource + 双向距离 (07#5.2) | ✅ 新增 |
| 调用点 | 12 处分散调用 computeLoopVia | `path-resolver.ts` 集中决策，其他模块读 RunPath | ✅ 集中化 |

## 4. 几何切片与渲染

### 4.1 现有双轨制

| 格式 | 函数 | 算法 |
|---|---|---|
| 旧格式 (无方向 MultiLineString) | `sliceGeoJsonPath` | stitch → snap → 距离检测 loop → 双向比较取短 → 可能拆为 MultiPolyline |
| 新格式 (方向分离) | `sliceDirectionalPath` | flatConcatCoords → station pair 逐对 snap → modular index 行走 → turf.lineSlice 逐段切 → dedup 拼接 |

### 4.2 新设计对应

| 现有步骤 | 新设计模块 | 变化 |
|---|---|---|
| stitchRoutes (贪心拼接) | `render-geometry.ts` `stitchEdgeGeometries` | 从贪心改为 edge sequence 顺序拼接 |
| 首尾距离 loop 检测 | `graph-builder.ts` 拓扑检测 | 从几何启发改为图论判定 |
| 双向比较取短 | `path-resolver.ts` §2.3 | 同逻辑，增加 viaRefs 和对称处理 |
| station pair 逐对切 | `render-geometry.ts` 按 `RunPath.edgeSequence` 逐 edge 取 geometry | edge 已拆分好，不再需要逐对切 |
| safeSliceToTail/FromHead | 不再需要 | edge 级拼接无需跨 seam 切分 |
| dedup 相邻 segment | `stitchEdgeGeometries` 端点重合检测 | 相同逻辑 |
| MultiPolyline 输出 | 不再需要 | edge sequence 天然连续 |
| 坐标 lng/lat ↔ lat/lng 转换 | 视渲染端约定 | 统一在渲染输出边界处理 |

**关键简化**：现有的双轨制源于"ML 未标准化为 edge → 需要动态切分 → 需要处理 seam 跨越"。新设计在 `normalizers.ts` 阶段已把 ML 拆为独立 edge，渲染只需按 edge sequence 顺序拼接坐标，不再需要 `turf.lineSlice` / `safeSliceToTail` / `safeSliceFromHead` 这些回退逻辑。

## 5. Geometry 缓存键

| 维度 | 现有实现 | 新设计 | 判定 |
|---|---|---|---|
| 键格式 | `{lineKey}_{fromId}_{toId}_{direction}` (仅环线带方向后缀) | 隐式包含在 `RunPath` 中 | 🔄 实现期决策 |
| direction='auto' 处理 | 调用 computeLoopVia 预解析为 up/down | RunSpec 的 directionHint 已在 path-resolver 中解析 | ✅ 等价 |
| 存储位置 | `segmentGeometries` Map + IndexedDB | 不在文档阶段约束 | 🔄 |

**说明**：新设计没有规定缓存策略（这是实现期决策）。但 `RunPath` 的确定性保证了相同输入必然产生相同 edge sequence，缓存键可以用 `RunSpec` 的哈希。

## 6. Landmark 显示

### 6.1 现有实现

| 项目 | 细节 |
|---|---|
| 数据源 | `Station.landmark: boolean` (store/index.ts:90) |
| 算法 | 从 fromIdx 沿运行方向走到 toIdx，收集最多 2 个 `landmark=true` 站名 |
| 环线特殊处理 | 到达 toIdx 后继续走，因为"环线为了收集 2 个 landmark 可以继续往后找" (railwayRouting.ts:386) |
| 非环线 | 到达 toIdx 停止，或到达数组边界停止 |
| 展示 | TripEditor: "新宿・渋谷 方面" (内回り/外回り selector 下方)；TripsPage: "经由 新宿、渋谷" |
| 实现点 | `getLandmarks` (railwayRouting.ts:354) + `getLandmarkVia` (geo.worker.js:352) — 两处独立实现同一算法 |

### 6.2 新设计对应

| 维度 | 判定 |
|---|---|
| Landmark 在计划中是否有对应 | ❌ **缺失**——当前 02-09 文档中未提及 landmark 概念 |
| 是否应纳入 | ✅ 应该——landmark 是现有 UI 功能，用户可见 |
| 归属模块 | `events.ts` 或新增 `landmarks.ts`，从属于"运行语义信息"而非路径决策 |
| 与新模型的关系 | Landmark 是 station 的静态属性，与事件系统和 `RunOrder` 自然匹配：沿 `RunOrder.orderPoints` 行走，收集 `landmark=true` 的 station |

### 6.3 新设计判定

Landmark 已在计划中定位：

- 数据：`ServicePattern.stationSequence[].landmark?: boolean` (07#4.3.2)
- 渲染：`render-geometry.ts` 新增 `collectRenderLabels` 方法，沿 `RunPath.nodeSequence` 收集 `landmark=true` 的站名 (03#2.8)
- **不是事件**：不经过 `events.ts`，不生成 `RunEvent`。纯渲染时接口
- **环线"越过终点继续走"逻辑不再需要**：RunPath.nodeSequence 已含完整路径，直接遍历即可，不需要现有代码中的模算术延伸逻辑

## 8. 迁移风险排序

| # | 风险点 | 严重度 | 说明 |
|---|---|---|---|
| R1 | parser.ts 站序反转逻辑 | **高** | 所有现有环线数据依赖此 invariant。adapter 必须保留此行为或显式转换 |
| R2 | 几何切片双轨制 | **中** | 旧格式 GeoJSON 仍需 adapter 处理；新核心链不再接触旧切片逻辑 |
| R3 | 12 处 computeLoopVia 调用散落 | **中** | 迁移后集中到 path-resolver，散落调用点逐步替换为读 RunPath |
| R4 | Landmark 未纳入计划 | **低** | 功能简单（boolean + walk + limit 2），后续补入不阻塞核心链 |
| R5 | 缓存键格式变更 | **低** | 实现期决策，不影响设计 |

---

## 9. 结论

现有环线实现的核心逻辑（模算术方向比较、站序方向参照、landmark 收集）在新设计中都有对应位置，**不需要推翻重来**。主要变化是：

1. **简化**：几何切片从"运行时动态切 ML"变为"标准化时已拆 edge+渲染时直接拼接"
2. **集中化**：方向决策从 12 处分散调用变为 path-resolver 一处
3. **显式化**：环线判定从隐式 bool+启发式变为显式 `LineTopology`
4. **缺失**：landmark 功能需要在事件层或独立模块中补上

## 10. 多服务共线场景验证

### 场景：山手线(绿) 与 崎京线(蓝) 共线新宿→池袋

物理层（infraLayer）只有一条边：

```
InfraEdge {
  id: "E_SHINJUKU_IKEBUKURO",
  geometry: <新宿→池袋的物理轨道坐标>,
  role: "main",
  name: "新宿-池袋本線"
}
```

服务层两个 ServicePattern 各自引用同一条物理边：

```
ServicePattern(Yamanote) {
  lineRef: "JR:Yamanote",
  edgeSequence: ["E_SHINJUKU_IKEBUKURO", "E_IKEBUKURO_TABATA", ...],
  stationSequence: [
    { nodeRef: "N_SHINJUKU", stopType: "mandatory_stop", landmark: true },
    { nodeRef: "N_MEJIRO",   stopType: "mandatory_stop", landmark: false },
    { nodeRef: "N_IKEBUKURO",stopType: "mandatory_stop", landmark: true },
    ...
  ],
  directionConvention: { forwardLabel: "内回り", reverseLabel: "外回り" },
  topologyType: "cyclic",
  cycleCheck: { isCycle: true, modularModulo: 30 },
  displayColor: "#80C241"   // 山手绿
}

ServicePattern(Saikyo) {
  lineRef: "JR:Saikyo",
  edgeSequence: ["E_SHINJUKU_IKEBUKURO", "E_IKEBUKURO_AKABANE", ...],
  stationSequence: [
    { nodeRef: "N_SHINJUKU", stopType: "mandatory_stop", landmark: false },
    // 目白不在崎京线的 stationSequence 里
    { nodeRef: "N_IKEBUKURO",stopType: "mandatory_stop", landmark: true },
    ...
  ],
  directionConvention: { forwardLabel: "北行", reverseLabel: "南行" },
  topologyType: "linear",
  displayColor: "#00A7DB"   // 崎京蓝
}
```

### 10.1 渲染连贯性

Yamanote 内回り run (新宿→池袋→田端)：

```
RunSpec { startRef: "N_SHINJUKU", endRef: "N_TABATA", directionHint: "clockwise" }
  → path-resolver 匹配 Yamanote ServicePattern
  → RunPath { servicePatternRef: "JR:Yamanote",
              edgeSequence: ["E_SHINJUKU_IKEBUKURO", "E_IKEBUKURO_TABATA", ...],
              nodeSequence: ["N_SHINJUKU", "N_MEJIRO", "N_IKEBUKURO", ...] }
  → render-geometry: 沿 edgeSequence 取每条 InfraEdge.geometry 拼接
  → 颜色取自 ServicePattern(Yamanote).displayColor = "#80C241" (绿)
  → 坐标连续（edge 首尾物理连接），无断点 ✅
```

崎京线北行 run (新宿→池袋→赤羽)：

```
RunSpec { startRef: "N_SHINJUKU", endRef: "N_AKABANE", directionHint: "up" }
  → path-resolver 匹配 Saikyo ServicePattern
  → RunPath { servicePatternRef: "JR:Saikyo",
              edgeSequence: ["E_SHINJUKU_IKEBUKURO", "E_IKEBUKURO_AKABANE", ...],
              nodeSequence: ["N_SHINJUKU", "N_IKEBUKURO", ...] }  // 没有目白
  → 同一段 E_SHINJUKU_IKEBUKURO，但颜色是 "#00A7DB" (蓝)
  → 坐标同样连续 ✅
```

**结论**：同一物理边 √ 各自颜色渲染 √ 坐标连贯 √

### 10.2 同一站台/事件区分

新宿站是同一个 InfraNode，但两条线的停站语义不同：

```
events.ts 生成 Yamanote 事件:
  platform_stop @ orderIndex 0, entityRefs: ["N_SHINJUKU"], servicePatternRef: "JR:Yamanote"
  platform_stop @ orderIndex 1, entityRefs: ["N_MEJIRO"],   servicePatternRef: "JR:Yamanote"  ← 有目白
  platform_stop @ orderIndex 2, entityRefs: ["N_IKEBUKURO"],servicePatternRef: "JR:Yamanote"

events.ts 生成 Saikyo 事件:
  platform_stop @ orderIndex 0, entityRefs: ["N_SHINJUKU"], servicePatternRef: "JR:Saikyo"
  // 目白不在崎京 stationSequence 中 → 无事件
  platform_stop @ orderIndex 1, entityRefs: ["N_IKEBUKURO"],servicePatternRef: "JR:Saikyo"
```

**结论**：同一物理站，不同 ServicePattern 的 `stopType` 决定不同事件序列 √

### 10.3 共线段 + 不同站台的场景

如果山手线和崎京线在新宿使用不同站台面（山手用 1/2 番线，崎京用 3/4 番线），站台绑定在物理层：

```
InfraArea { id: "A_PLATFORM_YAMANOTE_12", kind: "platform", ... }
InfraArea { id: "A_PLATFORM_SAIKYO_34",   kind: "platform", ... }

GraphRelation { type: "platform_serves_track", from: "A_PLATFORM_YAMANOTE_12", to: "E_SHINJUKU_IKEBUKURO" }
GraphRelation { type: "platform_serves_track", from: "A_PLATFORM_SAIKYO_34",   to: "E_SHINJUKU_IKEBUKURO" }
```

ServicePattern 的 stationSequence 可选指定平台：

```
stationSequence: [
  { nodeRef: "N_SHINJUKU", stopType: "mandatory_stop", platformRef: "A_PLATFORM_YAMANOTE_12" },
  ...
]
```

`events.ts` 生成 `platform_stop` 时携带 `platformRef`，下游渲染/UI 据此定位到具体站台面。

### 10.4 复线共线段

同一组复线物理边被两个 ServicePattern 共用：

```
InfraEdge { id: "E_UP_TRACK",   ... }   // 上行物理轨道
InfraEdge { id: "E_DOWN_TRACK", ... }   // 下行物理轨道

ServicePattern(Yamanote).edgeSequence   = [..., "E_UP_TRACK", ...]   // 内回り走上行轨
ServicePattern(Yamanote).edgeSequence   = [..., "E_DOWN_TRACK", ...] // 外回り走下行轨
ServicePattern(Saikyo).edgeSequence     = [..., "E_UP_TRACK", ...]   // 北行走上行轨
```

每个 ServicePattern 独立指定每条边用哪条物理轨道。渲染时只取 edgeSequence 中指定的边，**不会串线**。Dynamic offset 同理——偏移计划绑定在 ServicePattern 上，两条线的偏移方向/颜色各自独立。
