# 内容寻址：流程与接口重分析

> 内容寻址不是"加一个 hash 函数"。它改变的是模块间的调用契约、计算的可缓存性、以及调试复现路径。这份分析聚焦流程和接口层面的改动，不涉及哈希实现细节。

## 0. 先回答核心问题

- **是架构层面的重要调整**：它直接解决 run 计算一致性、缓存命中、可复现调试入口三件目前靠纪律维持的基础问题。
- **紧迫性在“设计决策”而不是“一次性重构全部实现”**：当前处于新架构设计期，`SystemContext/RunContext`、`graphId/runId`、缓存失效规则必须现在定稿；但内部纯函数不需要同一阶段全部改为 ctx 传递。
- **收益与成本比高**：先统一编排层契约即可获得一致性和复现收益，避免后续模块落地后再返工接口。

## 1. 当前接口的问题

主文档 03/04 的接口风格是显式多参数：

```ts
// 现状
buildRailGraph(input): BuildGraphResult
resolveRunPath(graph, spec, options?): RunPathResult
buildRenderGeometryPlan(graph, path, options?): RenderGeometryPlan
buildRunOrder(path): RunOrder
synthesizeTimeline(order, anchors?): TimelineResult
generateRunEvents(graph, runPath, timeline, options?): EventResult
```

问题不在"参数多"，而在于：

- **结果不可寻址**。每次调用都是新的，即使输入完全相同。无法判断"这个 graph 我已经算过了"。
- **一致性靠纪律**。`generateRunEvents(graphA, pathB, ...)` —— 没有任何东西阻止你传入不匹配的 graph 和 path。graphA 和 pathB 是否来自同一次求解？编译器不知道。
- **调试入口不统一**。要复现一次 run 的计算，需要收集 graph + spec + path + timeline + events 全部对象，传给各函数重放。没有单一入口。

## 2. 流程改变：从线性管道到可寻址计算

### 2.1 当前流程

```
input → graph → path → renderPlan → order → timeline → events
         ↓        ↓         ↓          ↓        ↓        ↓
       (各模块消费上游对象，产出下游对象，无缓存)
```

### 2.2 改变后

```
SourceInput
    │
    ▼
buildRailGraph ──→ SystemContext { graphId, graph }
    │                    │
    │    ┌───────────────┘
    │    ▼
    │  initRunContext ──→ RunContext { runId, graphId, spec, path: null, ... }
    │    │
    │    ▼
    │  resolveRunPath ──→ RunContext { ... path: RunPath }
    │    │
    │    ▼
    │  buildRenderPlan ─→ RunContext { ... renderPlan }
    │    │
    │    ▼
    │  buildTimeline ───→ RunContext { ... order, timeline }
    │    │
    │    ▼
    │  generateEvents ──→ RunContext { ... events }
    │
    ▼
  (graphId + runId 可缓存、可复现)
```

核心变化：

- **Graph 构建输出 `SystemContext`**：graph + graphId + diagnostics 封装为一个不可变容器。graphId 是内容的 sha256，同一输入必然同一 graphId。
- **Run 链每一步都输出 `RunContext`**：不是多个独立返回值，而是一个逐步填充的上下文对象。每个阶段接收 RunContext，返回新的 RunContext。
- **graphId 绑定到 RunContext**：`runId = sha256(graphId + spec)`。graph 和 run 的从属关系被编码进 ID，不可能传错组合。
- **同一 graphId + spec → 同一 runId → 可跳过全部计算**。

## 3. 接口改变

### 3.1 新核心接口

```ts
// ===== Graph 层 =====

// graph-builder.ts
function buildRailGraph(input: SourceBatchInput): SystemContext;
function validateConnectivity(ctx: SystemContext): SystemContext; // 返回追加 diagnostics 的新 ctx

// enrichment.ts
function enrichGraph(ctx: SystemContext): EnrichResult; // 返回 PatchSet[]，不直接改 ctx

// patch.ts
function applyGraphPatches(
  ctx: SystemContext,
  patches: PatchSet[],
): SystemContext; // 返回新 graphId 的 ctx

// ===== Run 层 =====

// path-resolver.ts
function initRunContext(ctx: SystemContext, spec: RunSpec): RunContext;
function resolveRunPath(ctx: RunContext): RunContext;

// render-geometry.ts
function buildRenderGeometryPlan(ctx: RunContext): RunContext;

// timeline.ts
function buildRunOrder(ctx: RunContext): RunContext;
function synthesizeTimeline(ctx: RunContext): RunContext; // anchors 从 ctx.spec.timetableAnchors 取

// event-anchors.ts
function resolveEventAnchors(ctx: RunContext): RunContext;

// events.ts
function generateRunEvents(ctx: RunContext): RunContext;

// ===== 快照 =====

// debug.ts
function exportRunSnapshot(ctx: RunContext): RunSnapshot;
```

### 3.2 关键接口决策

**决策 1：内部实现是否也用 ctx？**

不强制。ctx 是编排层与模块边界契约。内部可以用 ctx，也可以 destructure 出 graph/path/timeline 后调用纯函数。两种风格不冲突：

```ts
// path-resolver.ts 内部可以这样实现
function resolveRunPath(ctx: RunContext): RunContext {
  const { path, diagnostics } = resolvePathInternal(ctx.graph, ctx.spec);
  return { ...ctx, path, diagnostics: [...ctx.diagnostics, ...diagnostics] };
}

// resolvePathInternal 保持纯函数风格，方便单独测试
function resolvePathInternal(
  graph: RailGraph,
  spec: RunSpec,
): { path: RunPath; diagnostics: Diagnostic[] } {
  // ... Dijkstra ...
}
```

**决策 2：`options?` 去哪了？**

大部分 `options` 实际上是 `RunSpec` 的一部分（`eventPolicy`、`directionHint`、`timetableAnchors`）。它们已在 `ctx.spec` 中，不需要额外参数。少数真正的算法选项（如 Dijkstra 的 maxTransfers）放在 `RunSpec` 的可选字段中，或在 `initRunContext` 时传入。

**决策 3：哪些函数不改？**

- `normalizers.ts` — 标准化独立于 graph，输入输出不变。
- `geojson-contracts.ts` — 校验层，不涉及上下文。
- `ids.ts` — 加 `hashEntity` 方法是功能增强，不是接口改动。
- `adapters/*` — 输入适配，与上下文无关。

**决策 4：RunContext 是 `readonly` 的，不可变更新**

```ts
interface RunContext {
  readonly runId: string;
  readonly graphId: string;
  readonly graph: RailGraph; // 共享引用，不复制
  readonly spec: RunSpec;
  readonly path: RunPath | null;
  readonly renderPlan: RenderGeometryPlan | null;
  readonly order: RunOrder | null;
  readonly timeline: readonly TimelinePoint[] | null;
  readonly resolvedAnchors: readonly ResolvedEventAnchor[] | null;
  readonly events: readonly RunEvent[] | null;
  readonly diagnostics: readonly Diagnostic[];
}
```

每个阶段通过展开运算符返回新对象：`{ ...ctx, path: newPath }`。graph 作为共享引用不会被拷贝——15MB 的 graph 在所有 RunContext 中指向同一块内存。

## 4. 执行流程改变

### 4.1 主流程

```ts
// 构建（一次）
const sysCtx = buildRailGraph(input);

// 可选：补全
const enrichResult = enrichGraph(sysCtx);
if (enrichResult.patches.length > 0) {
  sysCtx = applyGraphPatches(sysCtx, enrichResult.patches);
}

// 求解（多次，按 RunSpec）
const runCtx = pipe(
  initRunContext(sysCtx, spec),
  resolveRunPath,
  buildRenderGeometryPlan,
  buildRunOrder,
  synthesizeTimeline,
  resolveEventAnchors,
  generateRunEvents,
);

// 快照
const snapshot = exportRunSnapshot(runCtx);
```

### 4.2 缓存边界

```
缓存键                缓存值              失效条件
─────────────────────────────────────────────────
graphId              SystemContext        Patch 应用后 graphId 变
runId                RunContext           graphId 变或 spec 变
```

缓存不是核心模块的职责——核心模块只负责计算和返回 ctx。缓存层在 `debug.ts` 的快照系统和 `DeployedSystem` 的导出层。

### 4.3 并行

多个 RunSpec 可以并行求解——每个 `initRunContext(sysCtx, spec)` 返回独立的 RunContext，互不干扰。graph 是共享引用（不可变），不需要锁。

## 6. 不做

- 不实现 `ComputationStore`（缓存持久化层）——这是实现期决策
- 不把内部纯函数全部改为 ctx 风格——接口边界用 ctx，内部保持显式参数
- 不引入增量计算（哪个 stage 没变就不重算）——这是优化，不是架构
- `RunContext` 不替代 `EditableRailGraphSnapshot`——后者是编辑/调试态，前者是计算态

## 8. 实施优先级（避免“要么全做要么不做”）

1. **本期必须落定（架构决策）**
   - `SystemContext/RunContext` 类型与不可变约束
   - `graphId/runId` 生成规则与缓存失效规则
   - 对外主流程签名（编排层）统一为 context 流
2. **下期按需推进（实现优化）**
   - 内部算法函数是否 ctx 化
   - 持久缓存与跨进程计算存储
   - 增量重算与 stage 级缓存

## 7. 与 15MB 数据的兼容

- graph 在 SystemContext 和所有 RunContext 中是**共享引用**——不是拷贝。100 个 RunContext 仍只有一份 graph 在内存中。
- `canonicalJson` 序列化只在哈希计算时发生（频率低：导入时、patch 时、导出快照时），不在每个 run 时发生。
- 独立系统各自一个 SystemContext，互不引用。
