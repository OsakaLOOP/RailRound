# Rail Graph v1 完全集成实施计划

## 1. 目标与当前判断

本文把当前 `rail-graph-v1` 核心雏形、`rail-graph-v1-mvp` 本地工作台、`rail-graph-aggregate` 聚合工作台，以及应用内 mileage UserEvent 接入层收敛为一条可执行的 staged PR 计划。

最终目标不是再做一个平行 demo，而是得到一个完整、规范、可用、简洁严密的 rail-graph 应用集成：

1. 固定底层 topo 事实、管理员 ServicePattern 模板、用户运行输出三层边界清楚。
2. MVP 与 aggregate 已超前完成的清洗、编译、跨 workspace、ServicePattern、cross-pattern、UserEvent 能被保留，但必须从 verify-only / workbench 状态收敛到正式 runtime / deployment 契约。
3. 应用内 mileage UserEvent 已接入的 UI/API 保留为用户事件产品面，但后续必须接到 `RunContext` / `TripResult` / deployed preset，而不是长期依赖旧 `railwayData` 线性站表。
4. 每个阶段都有通过性测试，测试覆盖该阶段的真实风险，而不是只证明文件能 import。

## 2. 当前资产与保留口径

### 2.1 已完成且应保留

- `src/rail-graph-v1/`
  - 已有分层类型：`base-topology.types.ts`、`service-template.types.ts`、`runtime.types.ts`、`graph.types.ts`、`event.types.ts`、`mileage-event.types.ts`。
  - 已有 topo 工具：`topology.ts` 提供 adjacency、lookup、platform binding、double-track aggregation、direction role helper。
  - 已有 pathfinding v2：line graph + IntentionChain + Yen/A* 搜索，入口为 `pathfinding-v2.ts`。
  - 已有 mileage-centric user event 核心：`mileage-events.ts`。
- `src/rail-graph-v1-mvp/`
  - 已有 Vite-dev-only 本地 pipeline：prepare / clean / annotate / compile / validate / export。
  - 已有 Senseki clean verify 与 pathfinding E2E 相关 fixture。
  - 应继续作为 admin/dev 数据准备工作台，不直接成为用户 runtime。
- `src/rail-graph-aggregate/`
  - 已有 aggregate workspace、compiled-topology/no-direction boundary、ServicePattern store、chain adapter、render plan、cross-pattern resolver、legacy/mileage UserEvent compatibility。
  - `loadAggregate()` 默认拒绝 no-direction verify fallback，这个产品边界必须保留。
- 应用内 mileage UserEvent
  - `src/rail-graph-v1/mileage-events.ts` + `src/utils/mileageUserEvents.ts` + `MileageEventsPanel` / `EventComposer` / `EventInspector` / trips / stats / global search 已形成用户事件产品面。
  - 这部分是计划外超额完成，应保留并迁移到正式 rail-graph 输出，而不是回滚。

### 2.2 不应直接保留为最终形态

- no-direction aggregate graph 只能保留为 verify substitute，不能进入产品默认加载。
- `src/utils/mileageUserEvents.ts` 当前使用旧 `railwayData` 站表构建线性 mileage context，只能作为兼容层。
- aggregate UI 中的 ServicePattern / event UI 是管理员工作台，不应直接等同用户端 runtime。
- pathfinding v2 当前仍偏管理员模板生成，不应让普通用户请求在运行时重新猜测底层路径。

## 3. 目标架构收敛

### 3.1 三层主链

正式链路固定为：

```text
Source/Annotated Workspace
  -> BaseTopologyLayer
  -> Confirmed ServicePattern
  -> RailGraph/SystemContext
  -> DeployedSystem + PathPreset
  -> TripPlanRequest
  -> TripResult + TripEvent + mileage projection
  -> App UI / UserEvent / SavedTrip
```

关键边界：

- `BaseTopologyLayer` 是固定事实，不放 prefer/avoid/score。
- `ServicePattern` 是管理员确认模板，不是普通用户运行时猜测空间。
- `PathPreset` 是部署给用户端的优先消费单位。
- `TripResult` 是用户端展示和保存的唯一规划输出。
- `UserEventV2` 的稳定锚仍是 mileage；地点、站、时间、行程只是创建/查询入口。

### 3.2 模块归属

| 层 | 正式模块 | 保留/迁移来源 | 产物 |
|---|---|---|---|
| 输入/编译 | `rail-graph-aggregate/topology-compiler.ts`，后续上移稳定 API | aggregate compiled-topology branch | `BaseTopologyLayer` |
| 模板编辑 | `rail-graph-aggregate/service-pattern/*` | aggregate PR1 | `StoredServicePattern` |
| 模板寻径 | `rail-graph-v1/pathfinding-v2*` | v2 line graph | candidate / trace diagnostics |
| 图容器 | `rail-graph-v1/graph.types.ts` + 新 builder/fingerprint | v1 types | `SystemContext` |
| 部署包 | 新 `deployment` builder | `deployment.types.ts` | `DeployedSystem` |
| 用户规划 | 新 planner / trip projector | `user-facing.types.ts` | `PlanTripResult` |
| 用户事件 | `mileage-events.ts` + app adapter | mileage UserEvent 超额实现 | `BoundMileageEvent` / `TripEvent` |

### PR1 · Runtime Graph Builder 与内容指纹

目标：

- 从 `BaseTopologyLayer + ServicePattern[] + warm stores` 组装正式 `RailGraph/SystemContext`。
- 明确 graphId 只覆盖 topo 热层，render/event/app artifact 分别有 fingerprint。
- 给 aggregate compiled-topology 产物提供正式进入 `SystemContext` 的入口。

主要文件：

- 新增 `src/rail-graph-v1/graph-builder.ts`
- 新增 `src/rail-graph-v1/fingerprint.ts`
- 修改 `src/rail-graph-v1/graph.types.ts`
- 修改 `src/rail-graph-v1/types.ts`
- 新增测试 `src/__tests__/rail-graph-system-context.test.ts`

通过性测试：

1. 同一 `BaseTopologyLayer + ServicePattern[]` 生成稳定 `graphId`。
2. 只改 geometry/display/eventLayer 不改变 `graphId`，但改变对应 fingerprint。
3. 改 edge adjacency / ServicePattern.edgeSequence / traceSequence 改变 `graphId`。
4. indexes 覆盖 `patternsByEdge`、`patternsByStation`、`edgesBySection`、`bindingsByEdge`。
5. no-direction aggregate 不能从默认产品入口生成 deployable SystemContext，除非测试显式 opt-in。

## 6. 分阶段 commit 规则

每个阶段独立提交，提交前至少满足：

1. `git diff` 已检查，确认没有无关文件。
2. 阶段指定测试 PASS。
3. `npx tsc --noEmit -p tsconfig.json` 对代码阶段 PASS。
4. 最终或用户要求提交前，执行根 `npm run build`，覆盖 src 与 blog。

建议 commit 形态：

- `docs(rail-graph): add v1 integration execution plan`
- `feat(rail-graph): build system context fingerprints`
- `feat(rail-graph): validate confirmed service templates`
- `feat(rail-graph): resolve service geometry paths`
- `feat(rail-graph): add runtime timeline and events`
- `feat(rail-graph): build deployed presets`
- `feat(rail-graph): add trip planner adapter`
- `feat(rail-graph): connect mileage events to runtime paths`
- `test(rail-graph): add integration verification gate`

## 7. 已知阻断与处理

- 真实 annotated compiled aggregate 数据仍是最终产品路径的关键输入。当前 no-direction fixture 只能支撑 verify substitute；PR1-PR2 必须继续保持默认产品入口拒绝 fallback。
- app 现有 `railwayData` 与 rail-graph deployed system 会并存一段时间。PR6-PR7 必须使用 adapter，不直接大改 store 主结构。
- UI 文案如有改动，必须同步四语言 locale。PR0-PR5 尽量避免用户可见文案。
- pre-commit 配置当前不在仓库根显式存在；若后续新增，应将其加入 PR8 gate。
