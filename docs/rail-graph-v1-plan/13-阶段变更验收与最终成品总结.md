# Rail Graph v1 阶段变更验收与最终成品总结

## 1. 总体状态

本文承接：

- `11-完全集成实施计划.md`
- `12-原始设计偏离审计与产品接入修正.md`

当前 rail-graph v1 已从单独 MVP / aggregate 工作台，收敛为一条可验证的 runtime / deployment / app adapter 主链：

```text
MVP/aggregate prepared data
  -> BaseTopologyLayer
  -> confirmed ServicePattern
  -> SystemContext
  -> DeployedSystem + PathPreset
  -> TripPlanRequest
  -> TripResult + runtimeArtifacts
  -> app adapter + mileage UserEvent projection
```

当前成品的核心判断：

1. rail-graph runtime、deployment、trip planner、mileage UserEvent adapter 已形成可运行闭环。
2. MVP 与 aggregate 的超额成果被保留为数据准备、管理员模板、验证和诊断资产，没有直接泄漏为用户端产品 schema。
3. 用户端 `TripResult` 已从内部 `RunPath` / `ResolvedGeoJsonPath` 中解耦；迁移期 app/debug 需要的内部结构放入 `runtimeArtifacts`。
4. 完整应用级默认数据源切换仍未完成；当前是正式 runtime 可用、app 通过 adapter 可接入、全 UI 默认消费仍需后续 PR。

## 3. 本轮产品契约修正验收

本轮修正重点不是推翻 PR0-PR8，而是把已经实现的能力从 MVP/debug 风格收紧为用户端可长期维护的产品契约。

已完成更改：

1. `TripPlanRequest` 不再要求或暴露 `patternRef`。
2. `TripResult` 不再公开 `internalRunPaths`。
3. `TripResultSegment` 不再公开顶层 `patternRef`、`lineRef`、`systemRef`、`direction`、`resolvedPath`。
4. 新增 `TripSegmentMileageProfile`，作为用户事件投影和保存可用的窄契约。
5. 新增 `TripRuntimeArtifacts` / `TripSegmentRuntimeArtifacts`，承载迁移期 adapter/debug 所需内部 `RunPath` 与 `ResolvedGeoJsonPath`。
6. `planTrip()` 支持无 preset 的 station-ref 请求自动选择 ServicePattern。
7. 单一 ServicePattern 无法覆盖时，`planTrip()` 可基于 stationSequence 交集发现共享站，输出多段 TripResult 和 transfer event。
8. `resolveRunPath()` 按请求起终点裁切 confirmed template，避免 B->C 请求返回 A->C 全路径。
9. app bridge 优先使用 `runtimeArtifacts`，mileage UserEvent 投影使用 `mileageProfile`，不再依赖公开 `resolvedPath`。
10. app 自动规划入口通过 `appRoutePlanner` 优先消费已加载 rail-graph runtime，runtime 缺失或当前 legacy UI 数据不可消费时回落旧 `findRoute()`。
11. 新增 `rail:deployment:build`，从 aggregate 持久化的 `aggregate-state.json + service-patterns.json` 构建 `SystemContext + DeployedSystem` bundle。
12. 新增 `rail:deployment:export`，把外部或上游构建好的真实 bundle 写到 app 默认加载 URL。
13. deployment build 对 `no-direction-graph` 默认失败，只有显式 `--allow-no-direction-verify` 可生成 verify-only bundle。
14. 自动规划得到的 rail-graph app trip 会保存 `railGraph.tripResult` 产品快照，默认不把 `runtimeArtifacts` 写入用户行程。
15. `TripEditor` 中任何手动改段、拖拽站点、交换起终点、增删段都会清除旧 `railGraph` 快照，避免手动段和 rail-graph 产品结果不一致。
16. `projectEventsToTrip(events, railwayData, trip)` 会优先使用保存的 `trip.railGraph.tripResult` 投影 mileage UserEvent，legacy segments 只作为 fallback。
17. `StatsPage`、`GlobalSearchModal` 和 `calculateLatestStats()` 已通过产品投影优先读取 `trip.railGraph.tripResult`，即使 legacy `segments` 缺失或过期，也能得到 rail-graph line summary、搜索文本、距离和 latest card geometry。

## 4. 最终成品继承关系

### 4.1 继承原始设计

已继承的设计目标：

1. 编译期与运行期分离：`BaseTopologyLayer`、`ServicePattern`、`SystemContext`、`RunContext` 边界清楚。
2. 管理员模板与用户运行输出分离：confirmed ServicePattern 是 admin/runtime 输入，TripResult 是用户产品输出。
3. 内容寻址和可复现运行：graphId、artifact fingerprint、runId、routeFingerprint、presetHash 已贯通。
4. 用户事件不参与寻路：mileage UserEvent 是投影和查询层，不反写 RunPath。
5. GeoJSON 与 topo 分层：geometry 可渲染可计程，但不是唯一图结构真源。
6. legacy app 兼容：旧路由、旧用户事件字段和旧 cloud 字段保持可读可用。

### 4.2 继承计划外超额成果

保留并规范化的超额成果：

1. MVP clean / annotate / compile / validate pipeline 继续作为 dev/admin 数据准备工作台。
2. aggregate workspace 的 ServicePattern、cross-pattern、compiled-topology、event aggregation 继续作为管理员和验证资产。
3. mileage-centric UserEvent 已经进入用户产品面，不回滚为纯设计文档能力。
4. app 内 trips / stats / search / map 相关用户事件消费逻辑继续保留，通过 adapter 逐步迁移底层数据源。

## 5. 最终成品整合情况

### 5.1 已整合闭环

已形成闭环的模块链：

| 模块 | 当前职责 | 可消费产物 |
|---|---|---|
| MVP pipeline | 本地数据准备、清洗、验证 | clean source / diagnostics |
| aggregate workspace | 管理员 ServicePattern、cross-pattern、UserEvent 聚合验证 | StoredServicePattern / verify summaries |
| graph builder | 构建 SystemContext 和索引 | graphId / indexes |
| runtime resolver | confirmed template 到 RunContext | RunPath / timeline / events / geometry |
| deployment builder | 固化用户端部署包 | DeployedSystem / PathPreset |
| trip planner | preset 或 station-ref 请求到 TripResult | TripResult / runtimeArtifacts |
| app trip adapter | rail-graph TripResult 到现有 app trip segment | AppRailGraphTripResult |
| saved trip snapshot | 保存产品级 rail-graph 行程结果，默认排除 runtime artifacts | Trip.railGraph.tripResult |
| product projection | TripResult 到 search/stats/latest cards 的产品消费模型 | ProductTripSegment / line summary / distance |
| mileage adapter | TripResult 到 mileage projection context | BoundMileageEvent projection |
| integration gate | 端到端验证命令 | `.verify/integration-summary.md` |

### 5.2 保持隔离的边界

必须继续保持的边界：

1. no-direction aggregate fallback 只能 verify opt-in，不能成为产品默认数据源。
2. `TripResult` 是用户端稳定契约，不承载完整内部 `RunPath` / `ResolvedGeoJsonPath`。
3. `runtimeArtifacts` 是 adapter/debug companion，不应成为所有 SavedTrip 的默认必填字段。
4. `mileageProfile` 可保存和投影，但不应被扩张成完整 runtime path。
5. aggregate UI 是管理员工作台，不直接等同用户端 trip planner UI。

## 8. 最终验收标准

完整、规范、可用、简洁严密的 rail-graph app 集成，应满足：

1. app 默认可加载 DeployedSystem，并能在缺失时安全 fallback。
2. 用户端请求只使用 preset 或站点/时间/方向等产品概念。
3. TripResult 可直接展示、保存、搜索、统计、投影 mileage UserEvent。
4. 内部 RunPath / ResolvedGeoJsonPath 只通过 runtimeArtifacts 或 debug 工具消费。
5. no-direction fallback、admin draft、heuristic trace 不进入产品默认 runtime。
6. legacy 数据不回归，旧用户事件和旧 trips 仍可显示、导出和搜索。
7. 集成 gate、TypeScript、build、pre-commit 在提交前通过或有明确环境说明。
