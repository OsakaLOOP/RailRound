# 拓扑分层与启发式边界补丁

本文作为 `rail-graph-v1-plan` 的补丁说明，不直接修改既有文档正文。旧文档中部分表述把底层固定拓扑、管理员模板编辑、运行期渲染输出混在一起；后续实现以本文边界为准。

## 1. 三个层次

### 1.1 底层数据与 topo

底层数据是站线级精确循迹的固定事实层。它包含轨道边、节点、邻接关系、站、站台、站台-股道绑定、停车标、特殊区间、源几何切片与必要的结构关系。

停车标不是启发式结果。停车标可以由数字、几何或导入数据自动生成候选，但只有经过筛选和人工确认后才进入 topo；进入 topo 后，它就是确定停站股道、站台、站和运行轨迹绑定的强制事实。

该层必须足够支撑以下问题的确定回答：

- 一次运行具体经过哪些边、哪些站线、哪些站台；
- 停站与通过分别绑定到哪个站、哪个站台、哪条 platform edge；
- 渲染和里程计算所需的分段 GeoJSON 应从哪些 edge slice 拼接；
- 哪些语义变化会导致 graphId 或已部署模板失效。

### 1.2 管理员 service 模板编辑流程

管理员编辑层负责从固定底层数据创建、修正、确认 service 模板。这里可以使用启发式：候选路径生成、候选评分、缺口提示、方向推断、优先经由/避免经由、冲突解释等。

启发式只存在于“生成或选择模板路径”的流程中。它的输出应是可审阅的候选、诊断和 patch；只有管理员确认后的结果才成为 `ServicePattern` 或已部署模板。

`ServicePattern` 不应表达运行时猜测。它是已经确认的 service 模板：有序 edge 序列、站线级停站/通过序列、方向约定、服务别和必要显示语义。跨线与否对终端用户不重要，用户看到的是已确认、可渲染、可计程的模板结果。

### 1.3 UI 渲染与里程计算输出

用户端和服务器运行时消费的是已拼接后的 GeoJSON 路径和向上传递的语义结构。它不重新暴露底层绑定编辑过程，也不在普通用户流程中重新运行管理员级路径启发式。

该层可以保留复杂结构：分段 geometry、edge measure、station/platform/stopping point 引用、事件锚点、里程、时间、显示标签都需要向上传递。分层不是简化数据，而是明确哪些内容是固定事实、哪些内容是编辑建议、哪些内容是最终运行输出。

## 2. 术语边界

- **固定 topo 事实**：经筛选确认后进入 graph/topo 的数据，包括站线级几何切片、站台绑定、停车标和硬性通行约束。
- **启发式**：只指管理员生成或选择具体路径时的规则、评分和建议，不指停车标或基础拓扑事实本身。
- **service 模板**：管理员确认后的精确 GeoJSON/edge 模板，允许携带复杂语义，但不应依赖用户运行时重新猜测。
- **用户运行输出**：从已确认模板生成的可渲染、可计程、可显示事件的结构。

## 3. 对既有文档的修正

- 旧文档中“路径搜索在 `ServicePattern.edgeSequence` 上运行”的说法应改为：管理员编辑层可以基于 topo 对候选路径进行搜索和评分；用户运行时优先消费已确认模板，只有管理员或后续协作编辑流程才进入候选生成。
- 旧文档中“物理 edge 不携带 stationRef，站序由 ServicePattern 承载”的说法需要补充：底层 topo 必须能表达站、站台、股道、停车标之间的固定绑定；`ServicePattern` 承载的是确认后的运行模板序列，不负责补足底层绑定事实。
- 旧文档中“补全/推断”相关内容需要区分：自动生成候选不等于进入 topo；进入 topo 前必须可审阅、可诊断、可确认。

## 4. 实现约束

- `types.ts` 作为类型唯一真源，应显式区分 base topology、admin template editing、resolved user output。
- `topology.ts` 应描述固定基础循迹拓扑，而不是仅描述连通图。
- `route_restriction` 这类约束必须分清：硬性基础约束属于 topo；偏好、评分、避免/优先经由属于管理员模板生成层。
- 服务器与普通用户 UI 只接收已确认、已拼接、可渲染的结果；底层编辑诊断和启发式痕迹不作为普通用户运行接口的必需部分。
