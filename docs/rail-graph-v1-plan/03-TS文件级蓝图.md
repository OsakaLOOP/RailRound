### 1.1 当前 MVP 本地工作台补充

当前 MVP 已在 `src/rail-graph-v1-mvp/` 形成独立 admin/dev 工作台，
不属于最终 `src/rail-graph-v1/` runtime 核心模块，但它已经验证了数据
准备到导出的本地闭环:

- `src/rail-graph-v1-mvp/app.ts`: 浏览器工作台 shell、workflow UI、编译和
  Senseki validation 编排。
- `src/rail-graph-v1-mvp/pipeline.ts`: workflow step、pipeline stage、
  project preset、task/artifact/workspace state 类型与 API client。
- `scripts/rail-graph-mvp-server.js`: Vite dev middleware，本地启动 Python
  GIS 脚本、查询/取消 task、枚举/读取 artifact。
- `vite.config.js`: 挂载 `railGraphMvpServerPlugin()`。

该工作台的 stage 名称是本地数据维护动作，不应直接并入最终
`graph-builder/path-resolver/timeline/events` 模块名。最终核心仍保持
`SystemContext -> RunContext` 的 compile/solve 分层。

## 2. 文件级职责与接口

### 2.1 `types.ts`
- 职责：定义核心领域类型（唯一真源）。
- 导出结构：
  - `RailEntityId`
  - `RailGraph`
  - `GraphNode`, `GraphRelation`
  - `InfraNode`, `InfraEdge`, `InfraArea`, `SpecialSection`
  - `ServicePattern`  (★ 服务线路：有序边/站序列、方向约定、停站模式、渲染标签)
  - `DoubleTrackRelation`, `RenderGeometryPlan`
  - `RunSpec`, `RunPlan`, `RunPath`, `RunPathResult`
  - `LoopDecision`
  - `RunEvent`, `TimelinePoint`, `EventAnchor`, `EventPolicy`, `EventPolicyRef`
  - `OffsetSmoothingPlan`, `OffsetGeometrySegment`
  - `PatchSet`, `PatchOp`, `EditableRailGraphSnapshot`
  - `Diagnostic`, `DiagnosticLevel`
  - `StationMeta`, `PathPreset`, `TripPlanRequest`, `PlanTripResult`
  - `TripResult`, `TripResultSegment`, `StationStop`
  - `TripEvent`, `SavedTrip`
  - `EntityAnnotation`, `ContributionStore`
  - `SystemContext`, `RunContext`, `RunSnapshot`
- 约束：仅类型，无实现函数。

### 2.2 `ids.ts`
- 职责：稳定 ID 生成与校验。
- 方法：
  - `buildStableId(input: StableIdInput): RailEntityId`
  - `parseStableId(id: RailEntityId): ParsedStableId`
  - `assertStableId(id: string): void`
  - `hashEntity<T>(entity: T): string`  // sha256(canonicalJson(entity))，用于缓存键/内容身份
  - `shortHash(hash: string, length?: number): string`  // 仅用于日志/UI 展示
- 输入：源命名空间、实体类型、稳定字段。
- 输出：符合规范的稳定 ID。

### 2.3 `contracts.ts`
- 职责：输入输出契约定义（schema 层，不绑定具体源）。
- 结构：
  - `SourceBatchInput`
  - `NormalizedEntityBatch`
  - `BuildGraphOptions`
  - `ResolveRunOptions`
  - `BuildRunPlanOptions`
- 方法：
  - `validateSourceBatch(input): ValidationResult`
- 约束：引用 `geojson-contracts.ts` 的 GeoJSON 输入类型，但不直接解析 GeoJSON geometry。

### 2.4 `geojson-contracts.ts`
- 职责：定义 `07` 中的 GeoJSON feature kind、geometry 组合与 properties 强类型。
- 导出结构：
  - `RailGraphGeoJsonInput`
  - `RailGraphFeatureProperties`
  - `PlatformAreaProperties`
  - `TrackGeometryProperties`
  - `SwitchPointProperties`
  - `SpecialSectionProperties`
- 方法：
  - `validateRailGraphFeature(feature): ValidationResult`
  - `detectLegacyGeoJsonKind(feature): RailGraphGeoJsonKind | undefined`
- 约束：只处理输入契约与兼容检测，不构建图。

### 2.5 `normalizers.ts`
- 职责：将多源数据标准化为统一实体。
- 方法：
  - `normalizeSources(input: SourceBatchInput): NormalizedEntityBatch`
  - `normalizeNode(raw): GraphNode`
  - `normalizeEdge(raw): GraphEdge`
  - `normalizeArea(raw): InfraArea`
  - `normalizeSpecialSection(raw): SpecialSection`
  - `normalizeEventAnchor(raw): EventAnchor`
- 行为：处理缺字段默认值，记录诊断，不中断主流程；`MultiLineString` 必须拆为可寻址 edge 或 edge slice。

### 2.6 `graph-builder.ts`
- 职责：构建统一多层图，输出 `SystemContext`。
- 方法：
  - `buildRailGraph(input: SourceBatchInput): SystemContext`
  - `buildInfraLayer(nodes, edges, areas, sections): InfraLayer`  — 纯物理连通（内部）
  - `buildServicePatterns(graph, batch): ServicePattern[]` — 从标准化数据提取服务线路（内部）
  - `linkAreasAndTracks(graph): RailGraph`（内部）
  - `attachDynamicPoints(graph, options?): PointAttachmentResult`（内部）
  - `validateConnectivity(ctx: SystemContext): SystemContext`
- 输出：`SystemContext { graphId, graph, diagnostics, createdAt }`。
- 行为：道岔等点到线的吸附在物理层动态计算；环线检测在 `buildServicePatterns` 中执行。同一 InfraEdge 可被多个 ServicePattern 引用。graphId 由 `sha256(canonicalJson(topo))` 生成（仅覆盖拓扑热层）。构建时同步填充反向索引（`patternsByEdge`, `patternsByNode`, `edgesBySection`, `tracksByPlatform`, `platformsByTrack`），支持 O(1) 的变更影响面查询与跨模块引用解析。

### 2.7 `path-resolver.ts`
- 职责：初始化 RunContext，在 serviceLayer 上求解运行路径。
- 方法：
  - `initRunContext(ctx: SystemContext, spec: RunSpec): RunContext`
  - `resolveRunPath(ctx: RunContext): RunContext`
  - `matchServicePatterns(spec, graph): ServicePattern[]` — 内部
  - `scoreCandidatePaths(ctx: RunContext): PathScore[]`
- 核心：路径搜索在 `ServicePattern.edgeSequence` 上运行。`resolveRunPath` 返回填充了 `path` + `candidateScores` 的新 RunContext。
- 约束：用户事件不参与寻路；存车线默认不进入普通候选。

### 2.8 `render-geometry.ts`
- 职责：从 RunContext 的 path + graph 生成渲染几何计划与渲染标签。
- 方法：
  - `buildRenderGeometryPlan(ctx: RunContext): RunContext`
  - `buildDynamicOffsetPlan(relation: DoubleTrackRelation, context): OffsetGeometryPlan` — 内部
  - `smoothOffsetTransitions(plan: OffsetGeometryPlan, options?): OffsetGeometryPlan` — 内部
  - `stitchEdgeGeometries(edgeRefs, graph): StitchedGeometry` — 内部
  - `collectRenderLabels(path: RunPath, pattern: ServicePattern): RenderLabels` — 内部
- 行为：返回填充了 `renderPlan` 的新 RunContext。物理 edge 与动态偏移可同时存在；动态偏移必须考虑平滑连接。landmark 为渲染时接口。

### 2.9 `timeline.ts`
- 职责：顺序优先时间轴生成。
- 方法：
  - `buildRunOrder(ctx: RunContext): RunContext`
  - `synthesizeTimeline(ctx: RunContext): RunContext`  // anchors 从 ctx.spec.timetableAnchors 取
  - `interpolateIntermediateTimes(points, strategy): TimelinePoint[]` — 内部
- 行为：`buildRunOrder` 返回填充 `order` 的 RunContext；`synthesizeTimeline` 返回填充 `timeline` 的 RunContext。所有插值点标记 `isSynthesized`。

### 2.10 `events.ts`
- 职责：事件投影与事件流生成。
- 方法：
  - `generateRunEvents(ctx: RunContext): RunContext`  // 返回填充 `events` 的 RunContext
  - `projectStationEvents(ctx: RunContext): PlatformEvent[]` — 内部
  - `projectJunctionEvents(ctx: RunContext): SwitchPassEvent[]` — 内部
  - `projectSpecialSectionEvents(ctx: RunContext): SpecialSectionEvent[]` — 内部
  - `projectSystemSwitchEvents(ctx: RunContext): SystemChangeEvent[]` — 内部
  - `projectOperationEvents(ctx: RunContext): OperationEvent[]` — 内部，按 ServicePattern.stationSequence[].operationType 触发
  - `projectScenicViewEvents(ctx: RunContext): ScenicViewEvent[]` — 内部
  - `projectUserDefinedEvents(ctx: RunContext): UserDefinedEvent[]` — 内部
  - `inferTransferMode(leftSegment, rightSegment, graph): TransferMode` — 内部
- 输出：有序 `RunEvent[]`，每条事件可追溯来源。
- 约束：用户事件作为事件附加层投影到 order/time/entity/geometry anchor，不影响 `path-resolver.ts`。

### 2.11 `event-anchors.ts`
- 职责：事件锚点解析、车窗绝景方向转换、用户事件相对绑定。
- 方法：
  - `resolveEventAnchors(ctx: RunContext): RunContext`  // 返回填充 `resolvedAnchors` 的 RunContext
  - `resolveScenicView(anchor, runContext): ScenicViewResolution` — 内部
  - `mapBearingToVehicleView(mapBearingDegrees, runDirectionBearingDegrees): VehicleViewDirection` — 内部
  - `bindUserEventToRun(anchor, order, timeline): BoundUserEvent` — 内部
- 行为：地图绝对方向可转换为运行车窗侧与相对方向。

### 2.12 `enrichment.ts`
- 职责：缺失数据补全与语义推断。
- 方法：
  - `enrichGraph(ctx: SystemContext): EnrichResult`  // 返回 PatchSet[]，不直接改 ctx
  - `inferDirectionForEdge(edge, context): DirectionInference` — 内部
  - `fillMissingPlatformRefs(node, context): Patch[]` — 内部
  - `inferDoubleTrackRelation(edges, options?: { hausdorffM?: number; angleDeg?: number; overlapRatio?: number }): DoubleTrackRelationInference` — 内部
  - `createSyntheticOffsetRelation(edge, context): Patch[]` — 内部
- 行为：补全必须伴随诊断。产生的 PatchSet 通过 `patch.ts` 应用到 SystemContext，产生新 graphId。

### 2.13 `diagnostics.ts`
- 职责：统一诊断模型与聚合。
- 方法：
  - `createDiagnostic(level, code, message, context): Diagnostic`
  - `collectDiagnostics(...groups): Diagnostic[]`
  - `hasFatalDiagnostics(list): boolean`

### 2.14 `patch.ts`
- 职责：支持随时增改（手工修补/自动修补统一入口）。
- 方法：
  - `applyGraphPatches(ctx: SystemContext, patches: PatchSet[]): SystemContext`  // 返回新 graphId 的 ctx
  - `previewGraphPatches(ctx: SystemContext, patches: PatchSet[]): PatchPreview`
- 结构：`PatchOp` 支持 add/update/remove/link/replace_geometry/add_event_anchor/update_event_policy。
- 约束：patch 不直接修改原始 GeoJSON/ORM 输入。应用后 graph 变更 = graphId 变更 = 所有基于旧 graphId 的 runId 失效。

### 2.15 `editing.ts`
- 职责：编辑输出主接口，组合 patch、snapshot、诊断和回放。
- 方法：
  - `createEditableSnapshot(ctx: SystemContext, runContexts?: RunContext[]): EditableRailGraphSnapshot`
  - `previewPatchSet(snapshot, patchSet): PatchPreview`
  - `applyPatchSet(snapshot, patchSet): EditableRailGraphSnapshot`
  - `exportPatchSet(patchSet): string`
- 行为：自动补全、人工修正、事件锚点新增都必须可预览、可应用、可导出。

### 2.16 `adapters/legacy-network-meta.ts`
- 职责：兼容旧 `networkMeta` 输入。
- 方法：
  - `adaptLegacyNetworkMeta(rawMeta, lineContext): AdaptedServiceSemantics`
- 覆盖：`common/byDirection/subSegments/events/systems` 全语义。

### 2.17 `adapters/orm-input.ts`
- 职责：ORM 数据转标准输入。
- 方法：
  - `adaptOrmRecords(records): SourceBatchInput`
  - `mapOrmStations(...)`
  - `mapOrmTracks(...)`
- 核心字段映射（参考）:
  - `orm.station_name` → `InfraNode.name`
  - `orm.station_id` → `InfraNode.id` (外部源 ID)
  - `orm.track_code` → `InfraEdge.track.trackCode`
  - `orm.line_id` → `InfraEdge.track.lineRef`
  - `orm.direction` (0/1) → `InfraEdge.track.direction` ("up"/"down")
  - `orm.is_storage` → `InfraEdge.track.role = "storage"`

### 2.18 `adapters/openrailwaymap-input.ts`
- 职责：OpenRailwayMap 对象转标准输入。
- 方法：
  - `adaptOpenRailwayMapObjects(objects): SourceBatchInput`
  - `extractPlatformTrackSwitchBridgeTunnel(...)`
  - `extractDoubleTrackRelations(...)`
  - `extractEventAnchors(...)`
- 核心标签 → kind 映射（参考）:
  - `railway=platform` + `public_transport=platform` → `platform_area`
  - `railway=rail` + `usage=main/branch` → `track_geometry` (role=main/branch)
  - `railway=rail` + `usage=siding` + `service=yard` → `track_geometry` (role=storage)
  - `railway=switch` → `switch_point`
  - `railway=rail` + `bridge=yes` → `special_section` (category=bridge)
  - `railway=rail` + `tunnel=yes` → `special_section` (category=tunnel)
  - `railway=rail` + `tracks=2` (双线) → 触发 `extractDoubleTrackRelations`

### 2.19 `debug.ts`
- 职责：前期调试接口与快照导出。
- 方法：
  - `buildGraphSnapshot(input, options?): GraphSnapshot`
  - `buildRunPlanSnapshot(graph, runSpec): RunPlanSnapshot`
  - `buildEditableRailGraphSnapshot(input, runSpecs?, options?): EditableRailGraphSnapshot`
  - `exportDiagnosticsReport(diags): DiagnosticsReport`
  - `exportSystemSnapshot(graph: RailGraph): SystemSnapshot`  // 导出带 graphId 的系统快照
  - `exportRunSnapshot(graphId, spec, path, renderPlan, order, timeline, events, diagnostics): RunSnapshot`  // 导出带 stageHashes 的运行快照

### 2.20 `index.ts`
- 职责：统一公共导出入口。
- 导出：
  - 类型导出（`types.ts`）
  - 主流程函数：`buildRailGraph / initRunContext / resolveRunPath / buildRenderGeometryPlan / buildRunOrder / synthesizeTimeline / resolveEventAnchors / generateRunEvents / applyGraphPatches / createEditableSnapshot`

### 2.21 MVP local pipeline adapter（当前已存在，非最终核心）

- 职责：把本地开发机上的 `D:\GIS\scripts` 数据准备脚本编排到 MVP
  工作台，生成可被 annotation/compile 阶段加载的 GeoJSON/JSON artifacts。
- 当前 stage:
  `diagnose`, `extract`, `emitFast`, `postFix`, `match`, `manifest`,
  `planBatches`, `mergeOverride`。
- 当前 workflow:
  `prepare`, `clean`, `annotate`, `compile`, `validate`, `export`。
- 约束：只作为 dev/admin adapter。不要从最终核心模块直接依赖 Vite
  middleware、DOM、localStorage 或本机路径。

## 3. 主流程

### 3.1 Graph 构建

```ts
const sysCtx = buildRailGraph(input: SourceBatchInput): SystemContext
// sysCtx = { graphId, graph, diagnostics, createdAt }

// 补全（可选）
const { patches } = enrichGraph(sysCtx);
if (patches.length > 0) {
  sysCtx = applyGraphPatches(sysCtx, patches);
}

// 校验
sysCtx = validateConnectivity(sysCtx);
```

### 3.2 Run 求解

```ts
const runCtx = pipe(
  initRunContext(sysCtx, spec),
  resolveRunPath,
  buildRenderGeometryPlan,
  buildRunOrder,
  synthesizeTimeline,
  resolveEventAnchors,
  generateRunEvents,
);
// runCtx.runId = sha256(sysCtx.graphId + canonicalJson(spec))
```

每次 RunSpec 调用产生独立的 RunContext。同一 (graphId, spec) 产生相同 runId，可缓存。

### 3.3 编辑输出

```ts
const snapshot = createEditableSnapshot(sysCtx, [runCtx]);
const preview = previewPatchSet(snapshot, patchSet);
const applied = applyPatchSet(snapshot, patchSet);
// applied 含新 graphId 的 SystemContext
```

## 4. 文件间依赖规则
- `types.ts` 不依赖任何业务文件。
- `index.ts` 只聚合导出，不写业务逻辑。
- `adapters/*` 只能依赖 `types/contracts/geojson-contracts/ids/diagnostics`，不得反向依赖 UI 层。
- `events/timeline/path-resolver/render-geometry` 依赖 `graph-builder` 产物，不直接消费原始输入。
- `event-anchors.ts` 可被 `events.ts` 调用，但不得调用 `path-resolver.ts`。

## 5. 实现期禁区
- 不在核心模块直接读 Zustand store。
- 不在核心模块直接操作 DOM 或 worker 端口。
- 不在核心模块引入 UI i18n 文案。
