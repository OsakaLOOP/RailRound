## 3. 审批重点

审批时建议按以下顺序确认：

1. `01` 是否准确描述了现有能力边界与兼容层现状。
2. `02` 的约束与默认行为是否满足后续可维护性与容错要求。
3. `03` 的文件划分是否决策完备，是否还留有实现期二次决策。
4. `04` 的主数据链是否闭环，是否覆盖你关心的上下行/复线/事件/时间。
5. `05` 是否能作为后续实现阶段的验收基线。
6. `07` 的 GeoJSON 输入、标准化 JSON、运行 JSON 与编辑输出契约是否足够承载新增对象。
7. `08` 的兼容性推理是否已经把新增约束回填到主架构。
8. `../rail-graph-v1/10-算法备考.md` 的算法候选是否已覆盖所有关键决策点，默认选择是否有充分理由，现有代码资产是否已被合理引用。
9. `../rail-graph-v1/15-常识逻辑检验.md` 的常识逻辑检验是否通过了深度均匀性和认知负担检查。
10. `10` 是否厘清了固定 topo、管理员启发式和用户运行输出的边界。
11. `11` 是否把当前 MVP、aggregate、runtime 与应用接入层收敛成可执行 PR 阶段和通过性测试。
12. `12` 是否证明实现没有把 MVP/admin 内部结构误暴露为用户端产品契约，并记录必要修正。
13. `13` 是否清楚总结每个阶段的更改、验收结果、最终成品继承关系、整合边界和剩余可执行 PR。
14. `14` 是否把“总体 70% / 用户端 90% / 数据端可不完美”的目标拆成可执行 PR、全接入面验收矩阵和需要拍板的 grill-me 决策。

## 4. 术语

- 统一多层图：基础设施层 + 运行服务层 + 事件附加层 + 运行时层。
- 顺序优先：先基于运行顺序确定事件序列，再兼容可选时刻表设定并插值。
- 稳定 ID：优先外部源 ID，缺失时使用可重复生成规则，保证同源同实体同 ID。
- 诊断：在不致命场景下记录补全与冲突，而非直接中断。

## 5. 当前拍板默认

已固定默认：

- 主键策略：显式稳定 ID
- 时间模型：顺序优先 + 可选时刻表
- 图结构：统一多层图
- GeoJSON 定位：原始几何与外部标签输入层，不作为图结构唯一真源
- 复线结构：物理 edge 与动态偏移计划同时兼容，每组复线至少具备其一；动态偏移必须考虑平滑连接
- 点吸附：道岔等点到线的吸附属于底层运行时/构建期动态计算，不要求输入提前写死
- 车窗绝景：可从地图绝对方向转换为运行车窗侧与相对方向
- 用户事件：作为额外时空语义层与车辆运行相对绑定，不参与寻路
- Infra/Service 分离：物理轨道不携带服务语义；ServicePattern 承载独立站序/方向/停站模式
