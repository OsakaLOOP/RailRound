# 常识逻辑检验

> 两条标准：
> 1. **深度均匀** — 不能某处很深、另一处用户要的"基本 xx"却没有
> 2. **复杂性在代码里，不在用户认知里** — 管理员和终端用户都不该感知内部图模型

## 1. 深度均匀性逐层检查

### 1.3 事件层

| 能力 | 深度 | 评级 |
|---|---|---|

- 谁触发编组事件？管理员手动标注？还是从 ORM 数据自动推断？

### 1.5 用户端抽象

| 能力 | 深度 | 评级 |
|---|---|---|
| TripResult 固化输出 | geometry + events + stations | ●●● |
| TripEvent 五种类型 | discriminated union | ●●● |
| PathPreset 模板 | 完整 | ●●● |
| **站台信息到达用户端** | **缺失** | ●○○ |
| **行程保存** | **缺失** | ●○○ |
| **规划失败的返回** | **缺失** | ●○○ |

**三个具体缺口**：

**缺口 1 — 站台信息不达用户端**

内部决策链 Layer 5 做了站台分配，`InfraArea` + `platform_serves_track` relation + `ServicePattern.stationSequence[].platformRef` 都有。但 `TripStopEvent` 和 `StationStop` 不携带 `platformName`。用户在东京站想知道"去几号站台乘车"，当前 TripResult 里没有。

**缺口 2 — 行程没有保存模型**

`TripResult` 是一次性快照，没有 "SavedTrip" 概念。用户规划完后想保存、下次再看、或者对比两个方案，没有对应结构。`TripResult` 本身可 JSON 序列化，只需 wrapper：

```ts
interface SavedTrip {
  savedId: string;
  name?: string;            // "周末镰仓出行"
  tripResult: TripResult;
  createdAt: string;
  systemId: string;         // 关联到哪个部署版本
}
```

**缺口 3 — 规划失败时用户看到什么**

当前只有 `TripResult` 成功路径。起终点不可达、无 ServicePattern 覆盖时，`planTrip` 返回值未定义。

## 2. 认知负担检查

### 2.1 终端用户

| 用户看到 | 内部对应 | 用户需要理解的概念 |
|---|---|---|
| "JR山手線 内回り" | ServicePattern.lineRef + directionConvention | 线路名 + 方向（日常概念） ✅ |
| "新宿 → 上野" | RunSpec | 起点 + 终点 ✅ |
| "经由 新宿、渋谷" | landmarkLabels | "经由"（日常概念） ✅ |
| "停靠 横浜 08:25" | TripStopEvent | 站名 + 时间 ✅ |
| "乗換: JR東海道線 → JR湘南新宿ライン" | TripTransferEvent | 换乘（日常概念） ✅ |
| 地图上的彩色线条 | geometry + displayColor | 无需理解 ✅ |
| "clockwise" / "counterclockwise" | — | **不暴露给用户** ✅ |
| InfraEdge / ServicePattern / adjacency | — | **不暴露** ✅ |

**终端用户认知负担：零新增概念。** 一切都是铁路出行已有概念。

### 2.2 管理员

| 操作 | 内部复杂度 | 是否隐藏 |
|---|---|---|
| 导入 ORM/GeoJSON 数据 | 多源适配 → RailGraph | ✅ 一键导入，全自动 |
| 查看自动生成的 ServicePattern | graph-builder 自动检测 | ✅ 展示可读结果 |
| 修正错误的站台绑定 | fillMissingPlatformRefs 的 warn + 候选列表 | ⚠️ 需理解 relation 概念，但候选列表已可读 |
| 创建换乘关系 | **不需要**——自动推导 | ✅ 管理员零操作 |
| 修正时刻表数据 | ServicePattern.defaultTimetable | ⚠️ 领域概念，不可避免 |
| 配置编组/解挂 | **当前没有清晰的管理界面** | ⚠️ 见 §1.3 缺口 |
| 理解诊断输出 | Diagnostic[] | ⚠️ 需确保每条 code 有对应的人类可读 message |

**管理员认知负担：合理。** 大部分复杂性被 auto-generation 吸收。

## 3. 短板汇总与优先级

| # | 短板 | 严重度 | 修复成本 | 建议 |
|---|---|---|---|---|
| 1 | 站台信息不到用户端 | **高** | 低（加字段） | 实现前修：`StationStop` 加 `platformName?` |
| 2 | 规划失败返回未定义 | **高** | 低（加 union） | 实现前修：`PlanTripResult` 用 discriminated union |
| 3 | 行程保存模型缺失 | 中 | 低（wrapper） | 第一轮迭代补 |
| 4 | 编组事件触发源缺失 | 中 | 中（需设计工作流） | 第一轮迭代补 |
| 5 | 管理批量操作薄弱 | 低 | 留给 UI 层 | 后续迭代 |
| 6 | 部署校验清单未细化 | 低 | 文档级 | 实现初期补 |

---

## 4. 总体判定

| 维度 | 评级 | 说明 |
|---|---|---|
| 深度均匀性 | **良好** | 物理/服务/事件/时刻四层深度一致。仅 2 项高优先级缺口 |
| 认知负担—终端用户 | **优秀** | 零新增概念 |
| 认知负担—管理员 | **良好** | 领域概念不可避免；auto-generation 吸收大部分技术复杂度 |
| 可修复性 | **优秀** | 6 项短板全部可修，无架构性阻碍 |

**结论**：计划通过常识检验。#1（站台信息）和 #2（失败返回）建议实现前修；其余可在迭代中补。
