# 编译框架、冷热分层、增量继承与反向索引

> 讨论文档。目标：范围初定、内在逻辑串联、以及对主设计文档的接入点识别。

## 0. 动机

当前设计（`rail-graph-v1-plan/`）已经有了完整的数据流和模块蓝图，但以下问题尚未被显式讨论：

- pipeline 前半段（建图）和后半段（求解）在性能特征、调用频率和缓存策略上完全不同，但当前被扁平地称为"主链"。
- 反向查询能力（edge 被哪些 ServicePattern 引用、站台归属于哪些线路等）在当前索引设计中缺位。
- 图数据内部存在巨大的访问频率差异，当前所有字段被同等对待。
- 图局部变更后，当前设计是全量重建（graphId 变了 → 所有 run 失效），缺少增量继承路径。

本文以**编译框架**为组织隐喻，串联上述问题，给出初步范围、内在逻辑和主文档接入点。

## 1. 编译框架：两阶段模型

### 1.1 核心类比

| 编译器概念 | 对应本系统 | 调用频率 | 延迟预期 | 数据量级 |
|---|---|---|---|---|
| **Lex/Parse** | `normalizers.ts` + adapters | 数据导入时 | 秒级 | 全量原始数据 |
| **Semantic Analysis** | `graph-builder.ts` + `enrichment.ts` | 数据导入时 | 秒~十秒级 | 全量标准化实体 |
| **IR** | `RailGraph` | 构建一次，多次读取 | — | ~15MB |
| **Compilation Unit** | `RunSpec` | 每次用户查询 | 毫秒级 | 单次查询参数 |
| **Optimization** | `path-resolver.ts` 候选评分 | 每个 RunSpec | 毫秒级 | 候选路径集 |
| **Codegen Targets** | `RenderGeometryPlan` / `EventStream` / `TripResult` | 每个 RunSpec | 毫秒级 | 单次 run 的产出 |
| **Build Artifact** | `RunSnapshot` / `TripResult` | 每个 RunSpec | — | 可缓存、可分发 |

### 1.2 关键分离

**编译期**（Build Phase）：`SourceInput → NormalizedEntityBatch → SystemContext`

- 慢，低频（数据导入时、patch 应用时）。
- 容忍延迟（秒到十秒级），但需要诊断完备。
- 输出 IR（`RailGraph`），可跨 run 共享。
- IR 不可变——任何变更产生新 IR + 新 graphId。

**运行时**（Solve Phase）：`RunSpec + SystemContext → RunContext → Artifacts`

- 快，高频（用户每次查询/规划）。
- 目标延迟：单次 solve < 100ms（15MB 图规模）。
- 同一 `(graphId, spec)` 必然同一 `runId`，可缓存。
- 多个 RunSpec 完全并行，共享同一份 IR。

### 1.3 设计影响

1. **编译期和运行时不应混在同一个 pipeline 描述中**。当前 `04-核心数据流与运行核心数据.md` 的"主数据链"把 `SourceInput` 和 `generateEvents` 写在同一行箭头里——这在工程上误导：前者是数据维护者的低频操作，后者是终端用户的高频操作。

2. **编译期需要进度模型**。`buildRailGraph` 在 15MB 数据上可能需要 5-15 秒。如果它是黑盒同步函数，UI 会卡死。在 `graph-builder.ts` 的接口设计中应预留进度回调或分阶段输出（如先出 InfraLayer 的 node/edge 数量，再出 ServicePattern 列表），即使实现期不做。

3. **IR 的稳定性是缓存的前提**。当前 `RailGraph` 包含 `provenance`、`diagnostics`、`annotations` 等元数据——这些字段的变更是否应触发 graphId 变化？这是下一节冷热分层的核心问题。

### 1.4 对主文档的接入点

- `04`：将"主数据链"拆为"编译期数据链"和"求解期数据链"两段，标注各段频率和延迟预期。
- `03`：在 `graph-builder.ts` 和 `index.ts` 的主流程描述中，标注 `// 编译期（低频）` 和 `// 求解期（高频）`。

## 2. 冷热分层：IR 内部的数据温度

### 2.1 问题

当前 `RailGraph` 是单层结构——所有数据（拓扑、几何、诊断、标注）在一个对象里。问题：

- **缓存键粒度过粗**：改了一个 annotation（冷数据），graphId 变化，所有 run 缓存失效——即使 annotation 不参与寻路。
- **序列化浪费**：导出 debug 快照时，如果只需要验证拓扑，仍然要序列化全量几何坐标。
- **内存布局无区分**：无法对高频访问的 adjacency 做针对性的紧凑存储。

### 2.2 热度分级

| 热度 | 数据 | 访问者 | 访问频率 | 影响 graphId？ |
|---|---|---|---|---|
| **热** | `infraLayer.nodes/edges/adjacency` | path-resolver（每次寻路） | 每次 run | **是** |
| **热** | `serviceLayer.servicePatterns[].edgeSequence/stationSequence` | path-resolver | 每次 run | **是** |
| **温** | `infraLayer.edges[].geometry`（坐标） | render-geometry, event-anchors | 每次 run 的渲染阶段 | **否**（见下） |
| **温** | `serviceLayer.servicePatterns[].displayColor/displayName/landmark` | render-geometry（渲染标签） | 每次 run 的渲染阶段 | **否** |
| **温** | `eventLayer.anchors/policies` | events.ts, event-anchors.ts | 每次 run 的事件阶段 | **否** |
| **冷** | `provenance` | debug.ts, 编辑界面 | 调试/审计时 | **否** |
| **冷** | `diagnostics` | debug.ts, 编辑界面 | 调试/审计时 | **否** |
| **冷** | `annotations`（EntityAnnotation） | 编辑界面 | 偶尔 | **否** |

关键判断标准：**是否影响 `RunPath` 或 `RunOrder` 的确定性输出？**
- 是 → 热数据，变更触发 graphId 变化。
- 否 → 温/冷数据，变更不触发 graphId 变化（仅触发 renderPlan/events 缓存失效）。

### 2.3 分离方案

```ts
interface RailGraph {
  // 热层：决定 graphId，变更 = 新 graphId = 所有 run 失效
  readonly topo: RailGraphTopo;

  // 温层：不影响寻路，变更不触发 graphId 变化
  // 但触发 renderId / eventId 变化（影响渲染和事件缓存）
  readonly geometry: GeometryStore;
  readonly display: DisplayStore;
  readonly eventConfig: EventLayerConfig;

  // 冷层：纯元数据，变更不影响任何缓存键
  readonly provenance: ProvenanceRecord[];
  readonly diagnostics: Diagnostic[];
}

interface RailGraphTopo {
  readonly infraLayer: InfraLayer;     // nodes, edges, adjacency（不含 geometry）
  readonly serviceLayer: ServiceLayer; // edgeSequence, stationSequence, topologyType
}
```

### 2.4 缓存键分层

```ts
interface SystemContext {
  readonly graphId: string;       // = sha256(topo) —— 只覆盖热层
  readonly renderFingerprint: string; // = sha256(geometry + display) —— 温层指纹
  readonly eventFingerprint: string;  // = sha256(eventConfig) —— 事件配置指纹

  readonly topo: RailGraphTopo;
  readonly geometry: GeometryStore;
  readonly display: DisplayStore;
  readonly eventConfig: EventLayerConfig;
  readonly provenance: ProvenanceRecord[];
  readonly diagnostics: readonly Diagnostic[];
}

interface RunContext {
  readonly runId: string;  // = sha256(graphId + renderFingerprint + eventFingerprint + canonicalJson(spec))
  //                           ↑ 三层都参与 runId，但可以分拆为 stage 级 hash
  readonly stageHashes: {
    readonly path: string | null;        // = sha256(runId + path)
    readonly renderPlan: string | null;  // = sha256(runId + path + renderPlan)
    readonly events: string | null;      // = sha256(runId + path + renderPlan + events)
  };
  // ...
}
```

### 2.5 一个折中

完全实现三层指纹可能过度设计。**最小可行版本**是只拆两层：

- `graphId` = sha256(topo) —— 热层
- `metaFingerprint` = sha256(geometry + display + eventConfig + diagnostics + provenance) —— 温+冷层合并
- `runId` = sha256(graphId + metaFingerprint + canonicalJson(spec))

改一个 annotation → `metaFingerprint` 变化 → 所有已缓存的 run 的 `runId` 变化。但这是可接受的：annotation 修改本来就不是高频操作，比全量重建 graph 便宜得多。

### 2.6 对主文档的接入点

- `02`：增补"热数据不变量"——定义哪些字段参与 graphId、哪些不参与。
- `07` §8.7：更新 `SystemContext` / `RunContext` 的字段定义，加入分层指纹。
- `07` §4.3：更新 `RailGraph` 结构，将 `topo` 从 `geometry/display/eventConfig` 中分离。

## 3. 增量继承：局部变更下的复用

### 3.1 问题

当前：graph 上任何变更 → `applyGraphPatches` 返回新 `SystemContext` + 新 `graphId` → 所有缓存 run 全部失效。

但 patch 的粒度差异极大：
- "新增一个 ServicePattern" → 旧 run 不受影响，但全被废弃。
- "改了一个 station 的 landmark 标签" → 旧 run 的 `RunPath` 完全有效，只是渲染标签需要更新。
- "改了一个 edge 的 geometry" → 旧 run 的 `RunPath`（拓扑）有效，但 `RenderGeometryPlan` 需要重算。
- "改了一个 edge 的 topology（切分/合并）" → 引用该 edge 的 run 的 `RunPath` 可能断裂。

### 3.2 变更分类

| 变更类型 | 示例 | 影响范围 | 复用粒度 |
|---|---|---|---|
| **元数据变更** | 改 annotation、provenance、diagnostic | 无 | 所有 run 完全复用 |
| **显示变更** | 改 displayColor、landmark、displayName | RenderGeometryPlan / TripResult 的显示字段 | RunPath 复用，renderPlan 重算 |
| **几何变更** | 改 edge 坐标（不改变拓扑连接） | RenderGeometryPlan | RunPath 复用，renderPlan 重算 |
| **事件配置变更** | 增/改 eventAnchor、eventPolicy | events | path + renderPlan 复用，events 重算 |
| **服务拓扑变更** | 改 ServicePattern.edgeSequence、stationSequence | 引用该 pattern 的 run | 受影响的 run 全量重算 |
| **物理拓扑变更** | 切分/合并/新增 edge | 引用该 edge 的所有 pattern + 所有 run | 受影响的 graph → pattern → run 逐级重算 |

### 3.3 最小可行方案：声明影响面，不自动执行增量

在设计阶段，不引入增量重算引擎，但引入**变更影响面声明**：

```ts
// patch.ts
interface PatchImpact {
  // patch 影响了哪些实体
  affectedEdges: EntityRef[];
  affectedNodes: EntityRef[];
  affectedPatterns: EntityRef[];
  affectedEventAnchors: EntityRef[];
  // 变更分类
  changeKind: "metadata_only" | "display_only" | "geometry_only" | "event_config" | "service_topo" | "infra_topo";
}
```

`applyGraphPatches` 返回 `{ ctx: SystemContext; impact: PatchImpact }`。

缓存层（不在本期实现，但设计应预留）可以通过 `impact` 判断：
- `metadata_only` → 所有缓存的 run 仍然有效。
- `display_only` → RunPath 缓存有效，renderPlan 缓存失效。
- `infra_topo` → 遍历 `affectedEdges` → `反向索引` → 找到受影响的 pattern → 找到受影响的 run → 只失效这些 run。

### 3.4 对主文档的接入点

- `02`：增补"增量继承约束"——patch 后旧 run 的复用条件由 changeKind 决定。
- `03` `patch.ts`：`applyGraphPatches` 返回值增加 `PatchImpact`。
- 不在本期实现增量引擎——`PatchImpact` 是接口契约，实现是下期的事。

## 4. 反向索引：补全查询能力

### 4.1 需要的反向查询

正面列出所有反向查询需求，按调用方分组：

**patch 影响分析**（`patch.ts`）：
- `edgeRef → 引用它的 ServicePattern[]`
- `edgeRef → 引用它的 DoubleTrackRelation[]`
- `nodeRef → 经过它的 ServicePattern[]`

**渲染标签收集**（`render-geometry.ts`）：
- `ServicePattern → 它的 landmark 站列表`（已有 stationSequence 可遍历，不需额外索引）

**事件锚点绑定**（`event-anchors.ts`）：
- `platform area → 它所服务的 track edge[]`
- `track edge → 它所服务的 platform area[]`

**调试与审核**（`debug.ts`、编辑界面）：
- `specialSection → 包含的 edge[]`
- `ServicePattern → 共享同一 InfraEdge 的其他 ServicePattern[]`

### 4.2 索引设计

```ts
interface RailGraphIndexes {
  // === 正向索引（已有） ===
  nodeById: Map<EntityRef, InfraNode>;
  edgeById: Map<EntityRef, InfraEdge>;
  areaById: Map<EntityRef, InfraArea>;
  sectionById: Map<EntityRef, SpecialSection>;
  patternById: Map<EntityRef, ServicePattern>;
  adjacency: GraphAdjacency;                        // node → 相邻 edge[]

  // === 反向索引（新增） ===
  patternsByEdge: Map<EntityRef, Set<EntityRef>>;   // edge → 引用它的 ServicePattern.id[]
  patternsByNode: Map<EntityRef, Set<EntityRef>>;   // node → 经过它的 ServicePattern.id[]
  edgesBySection: Map<EntityRef, Set<EntityRef>>;   // specialSection → 包含的 edge[]
  tracksByPlatform: Map<EntityRef, Set<EntityRef>>; // platform area → 服务的 track edge[]
  platformsByTrack: Map<EntityRef, Set<EntityRef>>; // track edge → 服务的 platform area[]

  // === 空间索引（略，见 §5） ===
  // spatialIndex: SpatialIndex;
}
```

全部反向索引在 `graph-builder.ts` 构建阶段同步填充，不增加运行时遍历成本。内存增量估算（15MB 图规模）：每个反向索引按 entry 数 × (key 8B + Set overhead ~64B + 平均每个 value 2-3 个 ref × 8B) ≈ 数百 KB 级别，可忽略。

### 4.3 对主文档的接入点

- `07` §4.3 `RailGraph` 的 `indexes` 增加上述反向索引字段。
- `03` `graph-builder.ts` 的 `buildRailGraph` 职责中增加"同步构建反向索引"。

## 5. 空间索引：接口预留

> 本节仅标记接口，详细讨论留待后续。

空间索引服务于三类操作：
1. **点吸附**（`graph-builder.ts`）：道岔点 → 最近 edge
2. **复线检测**（`enrichment.ts`）：两条平行 edge 的距离判定
3. **事件锚点绑定**（`event-anchors.ts`）：车窗绝景点 → 最近 edge

接口预留方案：

```ts
interface SpatialIndex {
  nearestEdges(point: GeoJSON.Position, k: number, maxDistanceM?: number): EntityRef[];
  edgesWithinDistance(edgeRef: EntityRef, maxDistanceM: number): EntityRef[];
  containingAreas(point: GeoJSON.Position): EntityRef[];
}
```

具体实现（R-tree / geohash / 网格分桶 / 暴力遍历）是实现期决策。设计阶段只确定接口契约和调用点。

**对主文档的接入点**：
- `07` §4.3 `RailGraphIndexes` 增加 `spatialIndex?: SpatialIndex`（可选，初期可用暴力遍历）。
- `03` `graph-builder.ts` 中 `attachDynamicPoints` 和 `enrichment.ts` 中 `inferDoubleTrackRelation` 的参数中引用 `SpatialIndex` 接口。

## 6. 概念交叉验证

以一次"管理员修改了一个 ServicePattern 的 displayColor"为例，验证各概念如何协同：

1. **编译框架**：这是温数据变更。不触发 re-compile（IR 的热层不变）。
2. **冷热分层**：`displayColor` 属于温层。`graphId` 不变（热层未变），但 `renderFingerprint` 变化。
3. **反向索引**：不需要——displayColor 变更不牵涉其他实体。
4. **增量继承**：PatchImpact = `{ changeKind: "display_only", affectedPatterns: [patternX] }`。引用 patternX 的 run 的 RunPath 缓存保留，renderPlan 缓存失效。

以一次"enrichment 推断出缺失的复线关系，新增了一条 dynamic_offset edge"为例：

1. **编译框架**：这是热数据变更。触发 re-compile（新增 edge → topo 变化 → 新 graphId）。
2. **冷热分层**：新增 edge 属于热层。`graphId` 变化。
3. **反向索引**：新 edge 加入 `patternsByEdge`、`adjacency` 等索引。通过 `edgesBySection` 判断是否属于已有 specialSection。
4. **增量继承**：PatchImpact = `{ changeKind: "infra_topo", affectedEdges: [newEdge], affectedPatterns: [...] }`（通过反向索引查找引用新 edge 的 pattern）。所有受影响 pattern 的 run 需要重算，其他 pattern 的 run 保留。

## 2026-05-24 MVP Local Pipeline Alignment

The current `docs/rail-graph-v1-mvp` workspace has implemented a local
admin/dev pipeline:

`prepare -> clean -> annotate -> compile -> validate -> export`

Its concrete stages are `diagnose`, `extract`, `emitFast`, `postFix`, `match`,
`manifest`, `planBatches`, and `mergeOverride`. This pipeline prepares local GIS
artifacts and source data for manual review, topology compile, validation, and
export. It is not the final user-facing solve/runtime pipeline.

The compile/solve separation described earlier in this file still stands. Treat the MVP local
pipeline as tooling around data maintenance and graph compilation. The final
runtime should still start from a fixed `SystemContext(graphId + graph)` and
produce a `RunContext`, render output, timeline, and events for each `RunSpec`.
