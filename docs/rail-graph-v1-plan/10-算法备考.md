**关键结论**：
- 点投影算法、环线方向决策、方向解析 → 几乎可直接 TS 化迁移。
- A* 路由框架、ML 贪心拼接 → 核心思路保留，输入/输出契约需适配新图模型。
- 暴力全扫描、静默回退、无诊断行为 → 新系统必须显式处理。
- 现有代码无诊断分级、无 patch 系统、无正式 ID 哈希 → 这些是新系统净新增能力。

## 1. graph-builder.ts — 图构建算法

### 1.1 点吸附（道岔 → 最近 edge）

| 项目 | 内容 |
|---|---|
| 候选 | ① 点到线段最近投影（垂直距离 + 线段参数 t）；② 端点就近吸附（优先吸附到最近节点而非线段内部）；③ 混合：先测节点距离，超过阈值再投影到线段 |
| 适用条件 | `InfraNode(kind=switch)` 缺少 `connectedTrackRefs`，或需要补全/校验已有连接 |
| 风险 | ① 简单投影可能吸附到错误的平行线（尤其是站场密集区）；② t 接近 0/1 时是否切分 edge 影响后续路径连续性；③ 距离超过合理阈值时（如 >50m）强行吸附会引入虚假连通 |
| 暂定默认 | 混合策略：阈值内（默认 30m）投影到最近线段；超过阈值不吸附，输出 `warn` 诊断；t 在 [0.05, 0.95] 外时优先吸附到端点而非切分 |
| 可复用已有实现 | `src/core/railwayRouting.ts:410` `projectedPoint` / `src/helper.js:18` — 点投影核心公式直接 TS 化；`src/core/railwayRouting.ts:464` `findNearbyStations` 排序截断技巧可用于限制候选 edge 数 |
| 附加规则：Edge 切分 ID 传播 | 当 t ∈ [0.05, 0.95] 需切分 edge 时：① 子 edge ID = `{parentId}-part{N}` (N=1,2 为切分后的前后段)；② graph-builder 返回 `splitMap: Map<EntityRef, EntityRef[]>` (旧 ID → 新 ID[])，供下游更新引用；③ 原 parent edge 标记 `inactive`，不删除以保留来源追溯；④ patch 系统记录 split op 供 snapshot 回放 |
| 相关文档 | [02#3.2](./02-设计约束与不变量.md#32-连通性不变量), [03#2.6](./03-TS文件级蓝图.md#26-graph-builderts), [08#2.3](./08-架构兼容性推理与调整建议.md#23-道岔是点对象) |

### 1.2 MultiLineString → 可寻址 edge 拆分

| 项目 | 内容 |
|---|---|
| 候选 | ① 按 segment 逐条拆为独立 edge，保留 `stitchGroupRef` 以备后续拼接；② 按站点/道岔等关键节点在交叉处切分；③ 保持整条 ML 作为单个 edge，内部用 measure 索引 |
| 适用条件 | 输入包含 `LineString` 数组的 `MultiLineString`，需要独立寻址每个线片段 |
| 风险 | ① 过度拆分导致 edge 数膨胀，路径搜索复杂度上升；② 拆分后丢失原 ML 的结构连续性（如需要整条线渲染时需反向拼接）；③ 不同源的 ML 坐标可能有微小偏移，简单按距离合并会产生假节点 |
| 暂定默认 | 方案 ①：逐 segment 拆为独立 edge，每条 edge 记录 `extraction.multiLineIndex` 与 `stitchGroupRef`。不主动在内部点切分（除非中间有道岔等关键节点） |
| 可复用已有实现 | `src/workers/geo.worker.js:212` `sliceDirectionalPath` — 跨 seam 拼接模式：逐 segment 独立寻址 + `stitchGroupRef` 统一拼接；`src/workers/geo.worker.js:202` `flatConcatCoords` — 简单拼接备选 |
| 相关文档 | [07#3.2](./07-GeoJSON与JSON层级契约.md#32-站线--股道), [03#2.8](./03-TS文件级蓝图.md#28-render-geometryts) |

### 1.3 连通性验证

| 项目 | 内容 |
|---|---|
| 候选 | ① BFS/DFS 检查全图连通分量，标记孤立子图；② 仅检查 RunPath 可达性（按需检查）；③ 基于 adjacency 索引做全量一致性校验（节点引用完整性 + edge 端点存在性） |
| 适用条件 | `buildRailGraph` 完成后、`resolveRunPath` 前 |
| 风险 | ① 全量检查在大型图上耗时；② 孤立子图不一定是 bug（如存车线、未启用的维修线），误报 fatal 会阻塞流程 |
| 暂定默认 | 方案 ③：先做引用完整性校验（每个 edge 的 from/to node 存在），再对主运行子图做 BFS 可达标记；孤立分量输出 `info`（含存车线、维修线等合理孤岛），引用缺失输出 `fatal` |
| 可复用已有实现 | 现有代码无正式连通性验证组件（当前只在路由失败时隐式暴露断连）。此项为净新增，但 `src/core/railwayRouting.ts:15` `buildStationIndex` 的索引构建模式可参考 |
| 相关文档 | [03#2.6](./03-TS文件级蓝图.md#26-graph-builderts), [05#2.3](./05-测试与验收映射.md#23-graph-builderts) |

### 1.4 站台面与站线绑定

| 项目 | 内容 |
|---|---|
| 候选 | ① 仅依赖显式 `trackRefs`；② 显式优先 + 缺失时基于面-线距离推断（最近 N 条线）；③ 基于面-线空间包含/相交关系推断 |
| 适用条件 | `InfraArea(kind=platform)` 缺少或需要验证 `trackRefs` |
| 风险 | ① 基于距离的推断可能绑定到相邻但不对应的股道（尤其是多层站场）；② 包含关系对不规则面和多线段精度敏感 |
| 暂定默认 | 方案 ②：优先显式 `trackRefs`；缺失时取面中心最近 3 条站线，按距离排序，输出 `warn` 诊断含推荐列表，不自动绑定（留待人工确认或 patch） |

## 2. path-resolver.ts — 路径决策算法

### 2.1 自动路径选择

| 项目 | 内容 |
|---|---|
| 候选 | ① Dijkstra（加权最短路径，edge weight = 物理长度）；② A*（启发式加速，启发函数 = 直线距离到终点）；③ K-最短路径（Yen's algorithm，输出 top-K 候选供评分） |
| 适用条件 | `RunSpec.pathOverride` 未指定，需自动从 `startRef` 到 `endRef` 找路径 |
| 风险 | ① Dijkstra/A* 在复线/上下行场景下，不引入方向约束会选到反向边或逆行；② A* 启发函数在铁路场景下（需沿轨而非直线）可能不如纯 Dijkstra；③ K-最短路径当 K 设置不当时输出过多噪声候选 |
| 暂定默认 | 方案 ①：加权 Dijkstra，基础 weight = edge 物理长度（米）。方向约束通过过滤 edge 候选集实现（仅允许匹配 `directionHint` 的边）。若需要多候选比较，K=3 用 Yen's 补充输出 |
| 可复用已有实现 | `src/core/railwayRouting.ts:78` `findRoute` — A* + 换乘罚分 + 同站换乘发现，核心框架可继承；`src/helper.js:204` `class MinHeap` — binary heap 直接 TS 化。关键改动：从 station-level 图升级为 edge-level 图；换乘罚分改为 relation 权重 |
| 相关文档 | [03#2.7](./03-TS文件级蓝图.md#27-path-resolverts), [02#4](./02-设计约束与不变量.md#4-路径与顺序约束), [04#2.5](./04-核心数据流与运行核心数据.md#25-runpath) |

### 2.2 候选路径评分

| 项目 | 内容 |
|---|---|
| 候选 | ① 单目标：总长度最短；② 多目标加权：长度 + 方向匹配度 + 换乘次数 + 轨道类型偏好；③ 分层评分：先按硬约束过滤（方向、存车线排除），再按软偏好排序 |
| 适用条件 | 路径存在多条候选（复线、环线、上下行可同时满足） |
| 风险 | ① 权重组设计不当导致不合理偏好（如过度惩罚换乘）；② 评分缺乏可解释性时调试困难 |
| 暂定默认 | 方案 ③：硬约束过滤 → 软偏好排序。软偏好权重：方向匹配优先（0.4）、总路径长度（0.3）、最少换乘（0.2）、优选主线（0.1）。评分原因写入 `PathScore.reason` |
| 可复用已有实现 | 现有代码无正式的多候选评分框架（当前 A* 返回单一路径）。此项为净新增。但 `src/core/railwayRouting.ts:37` `getTransferableLines` 的换乘发现逻辑可参考 |
| 相关文档 | [02#4.2](./02-设计约束与不变量.md#42-自动决策不变量), [03#2.7](./03-TS文件级蓝图.md#27-path-resolverts), [05#2.4](./05-测试与验收映射.md#24-path-resolverts) |

### 2.3 环线方向决策

| 项目 | 内容 |
|---|---|
| 候选 | ① 仅依赖 `directionHint` 显式指定（up/down/clockwise/counterclockwise）；② 自动检测：遍历两方向候选，选路径长度较短者；③ 自动检测：选与前后非环形段方向一致者 |
| 适用条件 | `LineTopology.topologyType = "cyclic"`，路径涉及环线，`directionHint` 为 `unknown` 或未指定 |
| 前置条件 | 环线判定不依赖猜测：`graph-builder.ts` 在构建阶段通过 `LineTopology.cycleCheck` 计算并存入 `infraLayer.topologyMeta[]`；人工数据若已标注 topology 则直接采用 |
| 方向参照 | `clockwise` = 站序索引递增方向 (0→1→...→N→0)；`counterclockwise` = 反向。非环线收到 cw/ccw 值降级为 `unknown` + 诊断 |
| viaRefs 优先 | 若用户指定 `viaRefs[]`（loopVia 语义），先找能经过该站的候选方向；若与 `directionHint` 矛盾，`viaRefs` 优先，`directionHint` 降级为 `unknown` 并输出 `warn` |
| 暂定默认 | 方案 ③：优先前后段方向一致性；其次方案 ② 选较短路径。若两条件冲突，标记 `warn` 诊断并取一致性优先。若两方向等长（完美对称环：长度差 < 1% 或 < 100m），优先 `clockwise`，仍不确定则输出 `warn` 诊断要求人工 override |
| 附加规则 | 环线方向决策结果全部写入 `RunPath.loopDecision`：含 `directionSource` (explicit/via_inference/distance_based/consistency_based)、完整数据 (fullCycleDistance/chosenDistance/alternativeDistance) 用于可解释性 |
| 可复用已有实现 | `src/core/railwayRouting.ts:331` `computeLoopVia` — 模算术距离比较，直接 TS 化迁移；`src/workers/geo.worker.js:307` `getDirectionForSegment` / `src/utils/networkDisplay.ts:188` `resolveDirection` — 逻辑一致 |
| 相关文档 | [01#1.3](./01-现状结构对比梳理.md#13-几何切片与方向处理), [02#3.2](./02-设计约束与不变量.md#32-连通性不变量), [07#4.3](./07-GeoJSON与JSON层级契约.md#43-railgraph), [07#5.1](./07-GeoJSON与JSON层级契约.md#51-runspec) |

### 2.4 存车线排除

| 项目 | 内容 |
|---|---|
| 候选 | ① 在 edge 候选集中直接过滤 `role=storage`；② 降低存车线 edge weight 至极大值（可被穷尽替代但显式 demand 可走）；③ 完全移除存车线节点从图中 |
| 适用条件 | 存在 `track.role=storage` 且非 manual override 或作业事件引用 |
| 风险 | ① 完全移除可能断开需要存车线作为唯一通道的路径（虽罕见但 fatal）；② 极大权重方式在 Dijkstra 下等同于过滤，但需额外处理 |
| 暂定默认 | 方案 ①：默认过滤，但 `pathOverride` 或 `operation_event_only` 引用时重新纳入候选。若过滤后无可达路径且存车线是唯一连接，输出 `error` 诊断并降级纳入 |
| 可复用已有实现 | 现有代码无存车线概念（当前仅以 `serviceable` 标记）。此项为净新增 |
| 相关文档 | [02#3.3](./02-设计约束与不变量.md#33-面线点区间不变量), [07#3.5](./07-GeoJSON与JSON层级契约.md#35-存车线), [08#2.5](./08-架构兼容性推理与调整建议.md#25-存车线通常不直接经由但有特殊意义) |

## 3. render-geometry.ts — 渲染几何算法

### 3.1 Edge 序列几何拼接

| 项目 | 内容 |
|---|---|
| 候选 | ① 直接按 edge sequence 顺序拼接坐标数组（首尾相接）；② 对相邻 edge 端点不重合的情况做线性插值补全；③ 对 MultiLineString 片段按 `stitchGroupRef` 合并后再输出 |
| 适用条件 | `buildRenderGeometryPlan` 需要输出可渲染的连续几何 |
| 风险 | ① 首尾坐标微小偏差导致渲染锯齿；② 线性插值补全在曲线上可能不自然 |
| 暂定默认 | 方案 ①：直接拼接。若端点距离 > 1m 记录 `warn`，> 10m 记录 `error`。不自动插值补全（留待数据修复 patch） |
| 可复用已有实现 | `src/workers/geo.worker.js:202` `flatConcatCoords` — 直接拼接；`src/helper.js:26` `stitchRoutes` — 贪心拼接（4 方向头尾距离匹配 < 1km），可用于有缺失的 ML 拼接；`src/workers/geo.worker.js:176-186` `safeSliceToTail`/`safeSliceFromHead` — 手动切片回退 |
| 相关文档 | [03#2.8](./03-TS文件级蓝图.md#28-render-geometryts), [04#2.5.1](./04-核心数据流与运行核心数据.md#251-rendergeometryplan) |

### 3.2 动态偏移计划生成

| 项目 | 内容 |
|---|---|
| 候选 | ① 沿运行方向左侧/右侧固定偏移（offsetMeters 常量）；② 按方向自动判断偏移侧（上行右、下行左）；③ 基于共享几何 + 偏移方向 + 平滑连接待拼接 |
| 适用条件 | `DoubleTrackRelation.geometryModes` 含 `dynamic_offset` 且缺少 `physical_edges` |
| 风险 | ① 固定偏移在曲线内侧/外侧不统一，视觉上轨道宽度不一致；② 偏移方向在上下行切换处可能反转；③ 偏移量过大时（如 >10m）在弯道处产生明显变形 |

## 6. enrichment.ts — 补全推断算法

### 6.1 缺失边方向推断

| 项目 | 内容 |

| 候选 | ① 基于 edge 端点坐标连线方位角推断（如方位角在 [NE, SW] 扇形内判为 up/down）；② 基于相邻已知方向 edge 的传播（图扩散）；③ 基于 edge 所属线路的全局方向标签（如全线 up 方向为 A→B） |

|---|---|
