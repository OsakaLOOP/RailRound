# 能力基座与后续扩展

> 明确当前设计已经提供的"基座能力"，以及后续深度语义绑定、模板化、自动规划与时刻表集成所需的扩展方向。不在此阶段实现，但确保架构不留阻碍。

## 1. 当前已具备的基座能力

### 1.1 物理/服务分离

```
infraLayer (物理)          serviceLayer (服务)
─────────────────────      ───────────────────────────
InfraEdge                   ServicePattern
  .geometry (坐标)            .edgeSequence → InfraEdge[]
  .role (main/storage/...)    .stationSequence → InfraNode[]
  .name (物理区段名)           .directionConvention (独立方向定义)
InfraNode                     .topologyType (每条线独立的拓扑)
  .id / .geometry              .displayColor / .displayName
InfraArea                   
  .geometry (站台面)         DoubleTrackRelation
GraphRelation                 .physical_edges / .dynamic_offset
  platform_serves_track      
```

这一层分离是后续所有能力的基石——管理后台绑定运行系统线，就是在创建/编辑 `ServicePattern`。

### 1.2 路径决策链

```
RunSpec (用户意图)
  → matchServicePatterns (匹配候选线路)
  → resolveRunPath (Dijkstra 自动 / manual override)
  → RunPath (确定路径)
  → RenderGeometryPlan (几何拼接 + 偏移 + 颜色)
  → Timeline (可选时刻表锚点 + 插值)
  → EventStream (事件序列)
  → EditableSnapshot (可审阅快照)
```

### 1.3 已支持的能力

| 能力 | 对应 | 状态 |
|---|---|---|
| 一条物理轨道承载多条运行线路 | InfraEdge ↔ ServicePattern[] (多对多引用) | ✅ |
| 每条线独立方向定义 | ServicePattern.directionConvention | ✅ |
| 每条线独立站序与停站模式 | ServicePattern.stationSequence[].stopType | ✅ |
| 每条线独立环线判定 | ServicePattern.topologyType + cycleCheck | ✅ |
| 复线物理边/动态偏移共存 | DoubleTrackRelation.geometryModes | ✅ |
| 渲染颜色与名称 | ServicePattern.displayColor/displayName | ✅ |
| 运行时刻表锚点 | RunSpec.timetableAnchors + timeline.ts 插值 | ✅ |
| 自动补全 + 诊断 + 人工修正 | enrichment.ts + patch.ts + editing.ts | ✅ |

## 2. 后续扩展方向（不在此阶段实现，但架构不阻碍）

### 2.1 站台选取语义绑定

**目标**：管理后台绑定好所有运行系统后，系统能自动推断某条线某个方向在某个站应该用哪个站台面。

**当前基座**：`platform_serves_track` relation + `ServicePattern.stationSequence[].platformRef?`（可选）

**扩展路径**：
- `platformSelectionRule` 挂在 ServicePattern 或 station 上：如 `{ prefer: "closest_to_exit", fallback: "any_available" }`
- 运行时 `render-geometry.ts` 或新 `platform-assigner.ts` 按规则解析 → 输出确定的 platformRef
- 不阻塞：当前 `platformRef` 已是可选字段，手动绑定先 work，自动规则后加

### 2.2 到发线/股道分配

**目标**：不只选站台面，还要选具体哪条股道（尤其大站多条到发线）。

**当前基座**：InfraEdge 有 `role` 区分 main/platform/storage；ServicePattern 的 `stopType` 表达停靠/通过

**扩展路径**：
- `trackAssignment` 类型：`{ servicePatternRef, stationRef, preferredEdges: EntityRef[] }`
- 可挂在 ServicePattern 上或独立 relation 表
- 不阻塞：当前 InfraEdge 已可按 role 过滤，手动指定 preferredEdges 即可

### 2.3 运行系统模板（Path Presets）

**目标**：管理后台绑定好所有 ServicePattern 后，预计算常用路径供用户直接选用——"山手线内回り 新宿→上野"作为可选模板，用户不用每次输起终点。

**当前基座**：
- ServicePattern 已是完整的运行线路定义
- RunSpec 可被序列化存储

**扩展路径**：
- `PathPreset` 类型：`{ presetId, runSpec: RunSpec, label: string, estimatedTime: string }`
- 管理后台预计算覆盖所有 station pair 的 path preset，或只精选常用区间
- 前端展示为可选模板列表，选中即填充 RunSpec
- 不阻塞：RunSpec 天然可序列化，存储即可复用

### 2.4 内置时刻表

**目标**：每条运行系统自带时刻表数据，用户选择模板后自动带入时刻，不要求手动输入锚点。

**当前基座**：
- `RunSpec.timetableAnchors` 已支持逐 run 指定锚点
- `timeline.ts` 已支持锚点间插值

**扩展路径**：
- `ServicePattern.defaultTimetable`：`Map<stationRef, { departureTime, arrivalTime, dwellSeconds }[]>`
- 可存储多套（平日/周末/临时）
- 用户选择模板时，系统自动把 defaultTimetable 映射到当前 run 的 timetableAnchors
- 不阻塞：timetableAnchors 是 RunSpec 级别的，ServicePattern 加字段即可

### 2.5 自动路径规划（全图范围）

**目标**：用户输入任意起终点，系统跨多条 ServicePattern 自动规划完整行程。

**当前基座**：
- `path-resolver.ts` 的 `matchServicePatterns` + Dijkstra
- transfer relation 在图中表达换乘点

**扩展路径**：
- 当前 Dijkstra 在单个 ServicePattern 的 edgeSequence 内运行
- 跨线规划需要：在图层级构建 "ServicePattern 间的 transfer graph"（station node 作为连接点，同一 station 的不同 ServicePattern 间有 transfer edge）
- 即：先在 servicePattern 级做路径搜索（选哪几条线），再在每条线内做 edge 级搜索
- 不阻塞：当前 station node + transfer relation 已是图的一部分，扩展为跨 pattern 搜索是算法层升级

### 2.7 速度曲线与分段限速

**目标**：时间估算不再依赖单一默认速度（60km/h），而是基于轨道物理特性（曲率、坡度、限速）和服务类型（各停/快速/特急）生成更精确的速度曲线——同时与时刻表数据互相校验。

**当前基座**：
- `InfraEdge.properties.maxSpeedKmh` — 每 edge 上限速（已有字段）
- `ServicePattern.serviceType` — local/rapid/express（已有字段，影响加减速频率）
- `timeline.ts` `interpolateIntermediateTimes` — 当前仅匀速插值

**速度曲线模型（草案，不实现）**：

```
一个 edge 上的速度曲线 = f(限速, 曲率, 坡度, 列车性能, 服务类型)

关键参数:
  v_max     = min(edge.maxSpeedKmh, trainType.maxSpeedKmh)     // 取轨道和列车孰低
  a_accel   = trainType.accelKmhPerSec                          // 加速率 (如 2.0 km/h/s)
  a_brake   = trainType.brakeKmhPerSec                          // 制动率 (如 3.0 km/h/s)
  dwell     = 停站时间 (由时刻表或 station 类型决定)

edge 分段:
  如果 edge 够长: 加速段 → 巡航段(v_max) → 制动段
  如果 edge 短:    加速段 → 立即制动 (未达到 v_max)
```

**最小新增类型（不实现，仅评估）**：

```ts
// 可选挂到 InfraEdge.properties 上
interface SpeedConstraints {
  curveRadiusM?: number;       // 曲率半径 → 导出限速
  gradientPermille?: number;   // 坡度千分比 → 影响加减速
  temporaryLimitKmh?: number;  // 临时限速 (如施工)
}

// 可选挂在 ServicePattern 上，也可独立
interface TrainPerformance {
  maxSpeedKmh: number;
  accelKmhPerSec: number;
  brakeKmhPerSec: number;
}
```

**时刻表与速度的互相校验（re-assure）**：

| 方向 | 机制 | 诊断 |
|---|---|---|
| 时刻表 → 检验速度 | 已知 timetable: Tokyo 08:00 → Shinagawa 08:06 (6min), 距离 6.8km → 平均 68km/h。若 edge.maxSpeedKmh=90，合理 ✅。若 edge.maxSpeedKmh=50，不可能 ❌ | `error: TIMETABLE_SPEED_CONFLICT` (时刻表推算速度超过轨道限速) |
| 速度 → 补全时刻 | 无 timetable 时，用速度曲线算出的 travel time + dwell time 作为 `isSynthesized=true` 的推定时刻 | `info: TIME_INFERRED_FROM_SPEED` |
| 阈值报警 | 推算速度与标称速度偏差 > 20% | `warn: SPEED_ANOMALY` |

这构成了闭环：**时刻表锚点越多，速度推断越准 → 无锚点的站时间越可靠。**

**加入时机评估**：

| 维度 | 评估 |
|---|---|
| 对现有类型系统的冲击 | 低——`InfraEdge.properties` 加字段、`timeline.ts` 插值升级、新增 `TrainPerformance`，都不碰类型核心 |
| 对时间精度的改善 | 显著——弯道减速、出站加速在山区线路（如中央线）和复杂站场（如东京站）影响明显 |
| 实现复杂度 | 中——加速/巡航/制动三阶段是经典运动学模型，实现成熟；真正复杂的是曲率半径→限速的经验公式 |
| 当前阶段的必要性 | **低**——默认 60km/h 匀速在大多数场景误差可接受（±15%），且用户可通过 timetableAnchors 手动修正关键站 |
| 依赖数据 | 曲率/坡度/临时限速数据源当前可能不具备（ORM 一般不提供），需要后续单独采集 |

**建议**：当前阶段不加入，但 `InfraEdge.properties` 已预留扩展字段（`maxSpeedKmh` 已存在，`curveRadiusM`/`gradientPermille` 可后加）。`timeline.ts` 的 `interpolateIntermediateTimes` 方法签名预留 `strategy` 参数（当前默认 `"uniform"`，后续可扩展为 `"speed_curve"`）。

### 2.8 用户共建数据

**目标**：终端用户可以对已部署系统中的实体贡献补充信息——如列车型号（E235/E237）、编组号、车辆设施（女性专用车位置）、实际观察等。管理员审核后可确认为系统级数据。

**当前基座**：
- `DeployedSystem` 是部署后的共享数据容器
- `TripNoteEvent` 承载用户个人备注（但局限在单次行程，不共享）
- `ServicePattern` 和 `InfraEdge` 已有 `properties` / `displayName` 等可扩展字段

**共建数据模型（草案，不实现）**：

```ts
// ========== 共建数据入口 ==========

/** 一条用户贡献——绑定到系统中任意实体 */
interface EntityAnnotation {
  annotationId: string;
  targetRef: EntityRef;                        // 绑定到 ServicePattern / Station / InfraEdge
  targetType: "service_pattern" | "station" | "edge";
  field: string;                               // 字段标识，如 "rollingStock", "wheelchairCar", "livery"
  value: string | number | boolean;
  confidence: "confirmed" | "reported" | "disputed";
  submittedBy?: string;                        // 用户标识（可选匿名）
  submittedAt: string;
  evidence?: string;                           // 来源说明，如 "2026-05 实地观察"
}

/** 共建数据状态——挂载在 DeployedSystem 上 */
interface ContributionStore {
  annotations: EntityAnnotation[];
  moderationQueue: string[];                   // 待审核的 annotationId 列表
}
```

**共建字段示例（非穷举，社区驱动扩展）**：

| field | targetType | value 示例 | 说明 |
|---|---|---|---|
| `rollingStock` | service_pattern | `"E235系"` | 常用列车型号 |
| `rollingStockDetail` | service_pattern | `"E235-0番台"` | 型号细分 |
| `wheelchairCar` | service_pattern | `4` | 轮椅位所在车厢号 |
| `womenOnlyCar` | service_pattern | `1` | 女性专用车厢号 |
| `livery` | service_pattern | `"湘南色"` | 涂装方案 |
| `stationExitNote` | station | `"北口出て左"` | 站出口备注 |
| `photoUrl` | station | `"https://..."` | 站照片 |
| `trainSetNumber` | service_pattern | `"08"` | 观察到的编组号 |

**管理后台审核流**：

```
用户提交 EntityAnnotation (confidence="reported")
  → 进入 ContributionStore.moderationQueue
  → 管理员审核:
    ✓ 确认 → confidence="confirmed" → 正式数据
    ✗ 拒绝 → 删除
    ? 存疑 → confidence="disputed" → 保留但标记
```

**对现有类型的冲击**：
- `DeployedSystem` 加一个 `contributions?: ContributionStore` 字段 — 可选，不破坏现有结构
- `EntityAnnotation` 是独立类型，不侵入 `ServicePattern` / `InfraEdge` 核心类型
- 共建数据与系统内部数据（`ServicePattern.stationSequence` 等）完全隔离——共建数据挂在外层，核心类型不变

**不阻塞**：`DeployedSystem` 已有 `stations` / `servicePatterns` 等引用目标，`EntityAnnotation` 只在外层引用它们的 ID。

## 3. 关键架构保证

当前设计有几个决策专门为上述扩展留了空间：

1. **`ServicePattern` 是独立实体，不是 InfraEdge 的属性**。这意味着后续给 ServicePattern 挂任何新字段（时刻表、站台规则、股道偏好）都不会污染物理层。

2. **`RunSpec` 是用户意图的序列化单位**。保存 RunSpec = 保存一条路径模板。后续 path preset 系统直接用 `RunSpec` 做存储格式。

3. **所有自动决策都输出诊断 + 可被 override**。自动站台选择、自动时刻表匹配这些后续能力，产出不确定时走 `warn` 诊断 + `PatchOp update_event_policy`，用户始终可以手动纠正。

4. **物理层和服务层通过引用关联，不通过继承**。`ServicePattern.edgeSequence` 是 `EntityRef[]`，不是 edge 对象嵌入。这意味着物理层升级（加信号机、加限速区）不影响已有 ServicePattern。

## 4. 不在此阶段做的（明确边界）

- 不设计具体的 `PathPreset` 存储格式和 UI
- 不设计时刻表数据源接入（GTFS/ODPT/手动录入）
- 不实现跨线全图自动规划的具体算法（两层 Dijkstra）
- 不设计信号机/进路/闭塞等运营安全级别建模
- 不设计多人协作编辑/版本管理/审核流

当前阶段保证：上述每一项在架构上都**有明确的扩展插入点，不需要推翻已有类型系统重做**。
