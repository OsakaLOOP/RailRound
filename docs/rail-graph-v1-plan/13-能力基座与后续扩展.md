# 能力基座与后续扩展

> 明确当前设计已经提供的"基座能力"，以及后续深度语义绑定、模板化、自动规划与时刻表集成所需的扩展方向。不在此阶段实现，但确保架构不留阻碍。

## 1. 当前已具备的基座能力

### 1.1 物理/服务分离

```
infraLayer (物理)          serviceLayer (服务)
─────────────────────      ───────────────────────────
InfraEdge                   ServicePattern
  .geometry (坐标)            .edgeSequence → InfraEdge[]
  .role (main/storage/...)    .stationSequence → InfraNode[]
  .name (物理区段名)           .directionConvention (独立方向定义)
InfraNode                     .topologyType (每条线独立的拓扑)
  .id / .geometry              .displayColor / .displayName
InfraArea                   
  .geometry (站台面)         DoubleTrackRelation
GraphRelation                 .physical_edges / .dynamic_offset
  platform_serves_track      
```

这一层分离是后续所有能力的基石——管理后台绑定运行系统线，就是在创建/编辑 `ServicePattern`。

### 1.2 路径决策链

```
RunSpec (用户意图)
  → matchServicePatterns (匹配候选线路)
  → resolveRunPath (Dijkstra 自动 / manual override)
  → RunPath (确定路径)
  → RenderGeometryPlan (几何拼接 + 偏移 + 颜色)
  → Timeline (可选时刻表锚点 + 插值)
  → EventStream (事件序列)
  → EditableSnapshot (可审阅快照)
```

### 1.3 已支持的能力

| 能力 | 对应 | 状态 |
|---|---|---|
| 一条物理轨道承载多条运行线路 | InfraEdge ↔ ServicePattern[] (多对多引用) | ✅ |
| 每条线独立方向定义 | ServicePattern.directionConvention | ✅ |
| 每条线独立站序与停站模式 | ServicePattern.stationSequence[].stopType | ✅ |
| 每条线独立环线判定 | ServicePattern.topologyType + cycleCheck | ✅ |
| 复线物理边/动态偏移共存 | DoubleTrackRelation.geometryModes | ✅ |
| 渲染颜色与名称 | ServicePattern.displayColor/displayName | ✅ |
| 运行时刻表锚点 | RunSpec.timetableAnchors + timeline.ts 插值 | ✅ |
| 自动补全 + 诊断 + 人工修正 | enrichment.ts + patch.ts + editing.ts | ✅ |

## 2. 后续扩展方向（不在此阶段实现，但架构不阻碍）

### 2.1 站台选取语义绑定

**目标**：管理后台绑定好所有运行系统后，系统能自动推断某条线某个方向在某个站应该用哪个站台面。

**当前基座**：`platform_serves_track` relation + `ServicePattern.stationSequence[].platformRef?`（可选）

**扩展路径**：
- `platformSelectionRule` 挂在 ServicePattern 或 station 上：如 `{ prefer: "closest_to_exit", fallback: "any_available" }`
- 运行时 `render-geometry.ts` 或新 `platform-assigner.ts` 按规则解析 → 输出确定的 platformRef
- 不阻塞：当前 `platformRef` 已是可选字段，手动绑定先 work，自动规则后加

### 2.2 到发线/股道分配

**目标**：不只选站台面，还要选具体哪条股道（尤其大站多条到发线）。

**当前基座**：InfraEdge 有 `role` 区分 main/platform/storage；ServicePattern 的 `stopType` 表达停靠/通过

**扩展路径**：
- `trackAssignment` 类型：`{ servicePatternRef, stationRef, preferredEdges: EntityRef[] }`
- 可挂在 ServicePattern 上或独立 relation 表
- 不阻塞：当前 InfraEdge 已可按 role 过滤，手动指定 preferredEdges 即可

### 2.3 运行系统模板（Path Presets）

**目标**：管理后台绑定好所有 ServicePattern 后，预计算常用路径供用户直接选用——"山手线内回り 新宿→上野"作为可选模板，用户不用每次输起终点。

**当前基座**：
- ServicePattern 已是完整的运行线路定义
- RunSpec 可被序列化存储

**扩展路径**：
- `PathPreset` 类型：`{ presetId, runSpec: RunSpec, label: string, estimatedTime: string }`
- 管理后台预计算覆盖所有 station pair 的 path preset，或只精选常用区间
- 前端展示为可选模板列表，选中即填充 RunSpec
- 不阻塞：RunSpec 天然可序列化，存储即可复用

### 2.4 内置时刻表

**目标**：每条运行系统自带时刻表数据，用户选择模板后自动带入时刻，不要求手动输入锚点。

**当前基座**：
- `RunSpec.timetableAnchors` 已支持逐 run 指定锚点
- `timeline.ts` 已支持锚点间插值

**扩展路径**：
- `ServicePattern.defaultTimetable`：`Map<stationRef, { departureTime, arrivalTime, dwellSeconds }[]>`
- 可存储多套（平日/周末/临时）
- 用户选择模板时，系统自动把 defaultTimetable 映射到当前 run 的 timetableAnchors
- 不阻塞：timetableAnchors 是 RunSpec 级别的，ServicePattern 加字段即可

### 2.5 自动路径规划（全图范围）

**目标**：用户输入任意起终点，系统跨多条 ServicePattern 自动规划完整行程。

**当前基座**：
- `path-resolver.ts` 的 `matchServicePatterns` + Dijkstra
- transfer relation 在图中表达换乘点

**扩展路径**：
- 当前 Dijkstra 在单个 ServicePattern 的 edgeSequence 内运行
- 跨线规划需要：在图层级构建 "ServicePattern 间的 transfer graph"（station node 作为连接点，同一 station 的不同 ServicePattern 间有 transfer edge）
- 即：先在 servicePattern 级做路径搜索（选哪几条线），再在每条线内做 edge 级搜索
- 不阻塞：当前 station node + transfer relation 已是图的一部分，扩展为跨 pattern 搜索是算法层升级

### 2.6 道岔/信号/作业点深度绑定

**目标**：道岔不只是点吸附，还要表达"从主线切到侧线需要经过哪个道岔、道岔当前开通方向、信号机位置"等深层次运营语义。

**当前基座**：
- `InfraNode(kind=switch)` + `attachDynamicPoints` 点吸附
- `OperationEvent` (coupling/decoupling)

**扩展路径**：
- `SwitchRouting` 类型：`{ switchRef, fromEdgeRef, toEdgeRef, direction: "normal" | "reverse" }`
- `SignalNode` 新增 InfraNode kind
- 这些是物理层扩展，不影响 serviceLayer 架构
- 不阻塞：当前道岔只表达了"在哪个位置切入"，更深的运营语义是叠加层

## 3. 关键架构保证

当前设计有几个决策专门为上述扩展留了空间：

1. **`ServicePattern` 是独立实体，不是 InfraEdge 的属性**。这意味着后续给 ServicePattern 挂任何新字段（时刻表、站台规则、股道偏好）都不会污染物理层。

2. **`RunSpec` 是用户意图的序列化单位**。保存 RunSpec = 保存一条路径模板。后续 path preset 系统直接用 `RunSpec` 做存储格式。

3. **所有自动决策都输出诊断 + 可被 override**。自动站台选择、自动时刻表匹配这些后续能力，产出不确定时走 `warn` 诊断 + `PatchOp update_event_policy`，用户始终可以手动纠正。

4. **物理层和服务层通过引用关联，不通过继承**。`ServicePattern.edgeSequence` 是 `EntityRef[]`，不是 edge 对象嵌入。这意味着物理层升级（加信号机、加限速区）不影响已有 ServicePattern。

---

## 4. 不在此阶段做的（明确边界）

- 不设计具体的 `PathPreset` 存储格式和 UI
- 不设计时刻表数据源接入（GTFS/ODPT/手动录入）
- 不实现跨线全图自动规划的具体算法（两层 Dijkstra）
- 不设计信号机/进路/闭塞等运营安全级别建模
- 不设计多人协作编辑/版本管理/审核流

当前阶段保证：上述每一项在架构上都**有明确的扩展插入点，不需要推翻已有类型系统重做**。
